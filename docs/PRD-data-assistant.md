작성일: 2026-10-26

## 1. 해결하려는 문제

에이전시와 고객사 관리자는 운영 숫자를 알고 싶을 때 화면을 돌아다니며 직접 세거나 비교한다. "오늘 대기 상담이 몇 건인지", "지난달보다 문의가 얼마나 늘었는지", "미답변 질문 중 가장 많은 게 뭔지" 같은 질문은 화면마다 흩어져 있고, 기간 비교는 화면에 아예 없다. 고객사가 자기 회사 데이터(작업 목록, 출고, 가입)를 같은 방식으로 묻고 싶어도 개발자가 쿼리를 짜 줘야 한다.

목표는 **채팅창에 말로 물으면 숫자·표·비교로 답하는 비서**다. 1차는 우리 플랫폼 데이터(상담·문의·챗봇 사용량)만 다루고, 2차에서 고객사의 자기 데이터베이스까지 넓힌다. 지식 주입(문서를 찾아 읽고 답하는 고객 대면 챗봇)과는 다른 엔진이며, 이 문서는 "계산해서 답하는" 쪽만 다룬다.

### 이 문서가 다루지 않는 것

- 고객 대면 챗봇의 지식 주입(URL·사이트맵·파일·표 데이터) — 기존 기능과 백로그
- 고객 대면 챗봇이 대화 중 재고·예약을 실시간 조회하는 것 — 3차 범위로만 언급
- 외부 서비스용 Open API — TBD

## 2. 제품 결정

| 항목 | 기본안 |
| --- | --- |
| 사용자 | 에이전시 소유자, 고객사 관리자. 상담 담당자는 2차에서 자기 고객사 범위로 검토 |
| 1차 데이터 | 우리 플랫폼의 상담(인계)·문의·견적·챗봇 대화량·미답변·거절 — 외부 연결 없음 |
| 2차 데이터 | 고객사가 연결한 자기 DB(PostgreSQL, MySQL). 읽기 전용 |
| 입력 | 자연어 한국어. 예: "오늘 대기 상담 몇 건?", "지난달 대비 문의 증감?" |
| 출력 | 한 줄 답 + 근거(기간·범위·계산 방식) + 필요 시 표/간단 추세. 결과가 많으면 상위 N건 |
| 질의 생성 | AI가 읽기 전용 SQL을 생성. 검증 통과한 것만 실행 |
| 안전 | SELECT만, 타임아웃 20초, 최대 1,000행, 허용 테이블·컬럼만, 개인정보 컬럼 제외 |
| 검증된 질문 | 관리자가 "맞다"고 확인한 질문은 질의를 고정해 재사용. 같은 질문은 항상 같은 계산 |
| 모호함 | 되묻기 1회. 답을 지어내지 않음 |
| 데이터 경계 | 에이전시는 자기 에이전시 전체, 고객사 관리자는 자기 고객사만. 집계 수치만 — 대화 본문은 보여주지 않음 |
| 설정 | 1차는 설정 없음. 2차는 연결 + 테이블·컬럼 한글 설명. SQL 작성 화면은 두지 않는다 |
| 비용 | 질문당 AI 호출 1~2회. 요금제 한도에 "월 비서 질문 수"로 편입 (기본안: 무료 100, 그로스 1,000, 프로 5,000) |

## 3. 사용자와 역할

### 에이전시 소유자

여러 고객사를 운영한다. "이번 주 고객사별 대기 상담", "지난달 대비 전체 문의 증감", "응답이 가장 느린 고객사"처럼 고객사를 가로지르는 질문을 한다. 데이터는 집계 수치만 본다(고객사 대화 본문은 보지 않는다 — 기존 분석 정책과 동일).

### 고객사 관리자

자기 회사 데이터만 본다. "오늘 처리할 문의 몇 건?", "답변 완료율 지난달 대비?", "미답변 질문 TOP 5". 2차에서는 자기 회사 DB를 연결해 "오늘 출고 몇 건?", "이번 달 신규 가입 지난달 대비?"를 묻는다.

### 상담 담당자 (2차 검토)

"내 담당 중 대기 몇 건?" 정도의 자기 범위 질문. 1차 범위에서는 제외.

### 플랫폼 마스터

질문 수·실패율·비용을 본다. 질문 내용은 보지 않는다.

## 4. 질문 유형과 답 (1차 — 우리 플랫폼 데이터)

| 질문 | 계산 | 답 예시 |
| --- | --- | --- |
| 오늘 대기 상담 몇 건? | 인계 상태 waiting, 오늘 | "대기 7건, 그중 1시간 넘게 기다린 건 2건이에요." |
| 지난달 대비 문의 얼마나 늘었어? | 문의·견적 접수 수, 이번 달 vs 지난달 | "184건 → 231건, +25%예요. 견적 요청이 가장 많이 늘었어요(+41%)." |
| 답변 완료율은? | 완료 / 전체, 기간 기본 30일 | "87%예요. 지난 30일 기준이고, 미완료 29건 중 보류 4건." |
| 미답변 질문 TOP 5 | 미답변 로그 묶음, 빈도순 | 표 5행 |
| 어느 챗봇이 대화가 제일 많아? | 챗봇별 세션 수 | 표 + "달빛 카페 안내가 전체의 62%" |
| 이번 달 세션 한도 얼마나 남았어? | 요금제 한도 − 사용량 | "5,000 중 3,120 사용, 1,880 남았어요. 이 속도면 27일쯤 소진돼요." |
| 현황판에서 지난달이랑 뭐가 달라졌어? | 대시보드 핵심 지표 6개를 두 기간 비교 | 지표별 증감 표 |

기간을 말하지 않으면 "최근 30일"을 쓰고 답에 명시한다. "오늘"은 Asia/Seoul 기준이다.

## 5. 주요 흐름

### 5.1 질문 → 답 (1차)

1. 사용자가 비서 채팅에 질문을 입력한다.
2. 서버가 사용자의 범위(에이전시/고객사, 허용 테이블)를 확정하고, 스키마 설명(우리가 작성한 한글 설명)과 질문을 AI에 준다.
3. AI가 `SELECT` 질의와 "계산 설명" 한 줄을 반환한다.
4. 검증: SELECT 단일문인지, 허용 테이블·컬럼만 쓰는지, 범위 조건(tenant_id/customer_id)이 반드시 포함됐는지(서버가 강제로 덧붙인다), 금지 컬럼이 없는지.
5. 읽기 전용 트랜잭션에서 실행. 타임아웃·행 제한.
6. 결과를 AI가 한국어 답으로 요약. 답 밑에 "근거: 최근 30일 · 달빛 카페 · 인계 상태 기준" 표시. "계산 보기"를 펼치면 질의와 원본 행.
7. 사용자는 👍/👎와 "정확해요" 버튼으로 피드백. "정확해요"는 검증된 질문으로 저장(§5.3).

### 5.2 모호할 때

"오늘 작업"이 마감일 기준인지 담당 기준인지처럼 해석이 둘 이상이면 **한 번만** 되묻는다: "마감일이 오늘인 문의? 아니면 오늘 접수된 문의?" 선택지를 버튼으로 준다. 두 번째도 모호하면 가장 흔한 해석으로 답하고 그렇게 해석했다고 밝힌다.

### 5.3 검증된 질문

관리자가 "정확해요"를 누르면 질문 문구·질의·설명을 저장한다. 이후 비슷한 질문(임베딩 유사도)이 오면 AI 생성 대신 저장된 질의를 쓴다. 검증된 질문은 설정 화면에서 목록으로 보고 이름을 붙이거나 삭제할 수 있다. 자주 쓰는 것은 비서 입력창 위에 칩으로 노출한다.

### 5.4 고객사 DB 연결 (2차)

1. 고객사 관리자가 "데이터 연결" 화면에서 DB 종류를 고른다.
2. 접속 정보는 두 길 중 하나: 직접 입력(암호화 저장, 재표시 없음) 또는 **연결 요청서** 내려받기(필요 권한·우리 서버 IP·읽기 전용 계정 만드는 법)를 호스팅 업체/개발사에 전달하고, 받은 정보를 입력.
3. 연결 테스트 → 테이블 목록(행 수·마지막 수정)이 뜬다. SQL은 어디에도 보이지 않는다.
4. 가져올 테이블을 체크하면 AI가 컬럼 한글 설명과 개인정보 추정 컬럼을 제안한다. 관리자는 설명을 고치고 제외할 컬럼을 체크한다.
5. "질문 3개 해보기"로 바로 테스트. 답이 맞으면 "정확해요"로 검증된 질문이 된다.
6. 저장하면 비서가 그 테이블을 질문 범위에 넣는다. 우리 플랫폼 데이터와 섞인 질문("우리 출고 건수와 챗봇 문의 수를 같이")은 2차에서 지원하지 않는다.

## 7. 서버·데이터 설계

### 7.1 스키마 설명 (1차)

우리 테이블 중 질문에 쓸 것만 **뷰**로 노출하고 AI에게는 뷰만 설명한다. 원본 테이블은 보이지 않는다.

| 뷰 | 출처 | 설명 |
| --- | --- | --- |
| `assistant_handoffs` | support_handoffs + chat_sessions | 인계 1건 = 1행. 고객사, 챗봇, 상태, 접수·시작·종료 시각, 대기 시간 |
| `assistant_requests` | 문의·견적 접수 | 고객사, 챗봇, 종류, 상태, 접수·완료 시각 |
| `assistant_sessions` | chat_sessions/chat_logs 집계 | 챗봇별·일별 세션 수, 메시지 수, 거절 수 — 본문 없음 |
| `assistant_unanswered` | 미답변 로그 | 질문 묶음 텍스트, 빈도, 마지막 시각 |
| `assistant_usage` | tenants + 월 사용량 | 요금제, 한도, 사용량 |

모든 뷰에 `tenant_id`, `customer_id` 컬럼이 있고, 서버가 사용자 범위를 WHERE에 **강제로** 덧붙인다(AI가 쓴 조건은 믿지 않는다). 대화 본문·이메일·전화번호 컬럼은 뷰에 넣지 않는다.

### 7.2 질의 생성·검증

- 프롬프트: 뷰 설명(한글), 오늘 날짜·시간대, 사용자 범위, 출력 형식(JSON: sql, explanation, needs_clarification?, choices?).
- 검증기: SQL 파서로 단일 SELECT인지, FROM/JOIN이 허용 뷰만인지, 함수가 허용 목록(집계·날짜·문자열)인지, `LIMIT` 없으면 1,000 부여. 실패 시 1회 재생성, 그래도 실패면 "이 질문은 계산할 수 없어요"로 답한다.
- 실행: 읽기 전용 트랜잭션, `statement_timeout 20s`, 결과 1,000행·2MB 상한. 2차 외부 DB는 별도 커넥션 풀(최대 2)과 동일 제한.
- 캐시: 같은 범위·같은 검증된 질문은 5분 캐시.

### 7.3 테이블

- `assistant_conversations` (id, tenant_id, customer_id, user_id, created_at) / `assistant_messages` (role, content, sql, rows_count, latency_ms, feedback, created_at)
- `assistant_verified_questions` (id, scope, title, question, sql, explanation, embedding, created_by, created_at)
- `data_connections` (2차: id, customer_id, kind, host/port/db/user 암호화, ssl, status, last_tested_at) / `data_connection_tables` (connection_id, table, enabled, column_notes JSON, excluded_columns)
- 감사: `access_audit_logs`에 `assistant.query`(실패 포함), `data_connection.create/update/delete/test`

### 7.4 비용·한도

질문 1건 = AI 2회(생성·요약) 기본. 검증된 질문 재사용 시 요약 1회. 월 질문 수를 요금제에 편입하고, 한도 80%에서 안내, 100%에서 "다음 달까지 검증된 질문만" 모드.

## 8. 개발자 없이 설정 가능해야 한다

- 1차는 설정이 없다. 로그인하면 바로 질문한다.
- 2차 연결에서 사용자가 보는 것은 "DB 종류 선택 → 요청서 내려받기 또는 정보 입력 → 연결 테스트 → 테이블 체크 → 컬럼 설명 확인 → 질문 3개 테스트"뿐이다. SQL·포트 번호·드라이버 이름은 화면에 두지 않는다(접속 정보 입력란 제외).
- 컬럼 설명은 AI가 컬럼명·샘플 값으로 초안을 쓴다. 사용자는 틀린 것만 고친다.
- 개인정보 추정 컬럼(이름·전화·이메일·주소·주민번호 패턴)은 기본 제외로 체크돼 있다.

## 9. 보안·개인정보

- 비서는 **집계와 목록**만 답한다. 대화 본문, 고객 연락처는 1차 뷰에 없다. 2차는 관리자가 제외한 컬럼을 절대 읽지 않는다.
- 외부 DB 접속 정보는 `lib/crypto.ts`로 암호화 저장, 로그에 남기지 않는다. 연결 삭제 시 즉시 파기.
- 외부 DB 호스트는 공개 주소만 허용(기존 웹 수집기의 사설 IP 차단 규칙 재사용). 고객사가 우리 서버 IP를 허용해야 연결된다.
- 질의 실행은 읽기 전용 트랜잭션. 쓰기 시도는 검증기에서 막고 감사 로그에 남긴다.
- 질문·답은 해당 에이전시/고객사 범위에만 보인다. 마스터는 건수·비용만 본다.

## 10. 구현 순서

1. **1차-A**: 뷰 5개 + 질의 생성·검증·실행 파이프라인 + 단위 테스트(검증기, 범위 강제)
2. **1차-B**: 에이전시 `/assistant` 화면, 답 블록, 피드백, 검증된 질문 저장·칩
3. **1차-C**: 고객사 데스크 `/customer/{id}/assistant`, 분석 화면의 "비서에게 묻기", 마스터 집계, 요금제 한도
4. **2차-A**: `data_connections` + PostgreSQL 커넥터(연결 테스트·테이블 목록·컬럼 설명 초안·요청서 PDF)
5. **2차-B**: MySQL 커넥터, 개인정보 컬럼 추정, 질문 3개 테스트 흐름
6. **3차 (별도 PRD)**: 고객 대면 챗봇의 허용 질의(재고·예약) 실시간 조회

각 단계는 독립 PR, 통합 브랜치 → 검토 → main 순서를 따른다.

## 12. 출시 기준과 남은 결정

출시 기준: A1~A8 통과, 검증기 단위 테스트, 100개 질문 샘플에서 "틀린 답을 자신 있게" 낸 비율 5% 이하(사람이 채점), 평균 응답 6초 이하.

남은 결정:
- 요금제 편입 수치(무료 100 / 그로스 1,000 / 프로 5,000)가 적절한지
- 상담 담당자에게 1차부터 열지 여부(자기 범위만)
- 2차 외부 DB에서 "우리 데이터와 섞인 질문"을 언제 허용할지
- 답에 간단 차트(막대·추세)를 넣을지, 1차는 표까지만
