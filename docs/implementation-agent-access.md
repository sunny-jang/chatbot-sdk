# 상담사 로그인·고객사 권한 — 구현 기록

기준: 2026-10-21 · 브랜치 `codex/workspace-redesign`  
제품 기준: [PRD](PRD-agent-login-and-customer-access.md)

## 현재 상태 (2026-10-22)

고객사 전용 상담 포털을 구현하고 격리 로컬 DB에서 검증했다. 운영 배포·운영 DB 이관은 아직 적용하지 않았다.

- 에이전시는 `/customers`에서 고객사 생성, 봇 연결, 담당자 초대를 관리한다.
- 고객사 담당자는 별도 `customer-credentials`로 로그인하며 tenant/admin 권한을 받지 않는다.
- 고객사별 상담함, 문의·견적, 관리자용 담당자 관리 화면을 제공한다.
- 모든 고객사 API는 현재 DB 멤버십을 다시 검사한다. 다른 고객사 데이터와 에이전시 비밀값 API 접근을 거부한다.
- 동시 상담 수락, 실제 작성자 기록, 중복 전송 방지, 종료 후 답변 차단을 처리한다.
- 초대·이메일 확인·비밀번호 재설정은 해시 토큰과 만료·단일 사용을 적용한다. 실제 메일 발송은 환경 설정이 필요하다.
- 기존 에이전시 인증은 유지하며 신규 가입·로그인 시 사용자/기본 고객사를 안전하게 연결한다. 고객사 Google 로그인과 전체 기존 API의 사용자 기반 전환은 후속 범위다.

### 서브도메인

`CUSTOMER_PORTAL_ORIGIN`에 고객사 상담 포털의 정확한 origin을 지정한다. 로컬 값은 `http://desk.localhost:3012`, 에이전시는 `http://localhost:3012`다. 포털 호스트의 `/login`, `/`는 고객사 화면으로 연결된다. 쿠키 Domain을 상위 도메인으로 넓히지 않는다. 서브도메인 자체는 고객사 권한을 부여하지 않는다.

운영에서는 선택한 `desk` 호스트를 동일 앱 배포에 연결하고 DNS/TLS를 설정해야 한다. `AUTH_URL`은 에이전시의 정확한 origin으로 유지한다. `RESEND_API_KEY`, `AUTH_FROM_EMAIL` 및 발신 도메인 검증을 설정해야 초대 메일이 발송된다. 설정이 없으면 503을 반환하며 이메일 확인을 우회하지 않는다.

### 검증

- 관련 단위 회귀 114개 통과.
- 격리 DB 권한·상담·초대·재설정 검사 22개 통과(트랜잭션 롤백).
- 실제 HTTP 로그인·호스트 분리·고객사 격리·동시 수락·초대 검사 24개 통과.
- 빌드 통과. 브라우저에서 담당자 로그인 → 자기 고객사 상담함 자동 이동과 문의 화면을 확인했다.
- 증빙: `docs/verification/customer-portal-2026-10-22/`, HTML 전체 QA 문서 하단.
- 메일 실발송, 운영 DNS/TLS, 운영 이관·복구 리허설은 미실행이다. 기존 전체 QA 실패 항목을 이번 포털 검사로 통과 처리하지 않았다.

## 이관 실행

먼저 백업과 복구 리허설이 가능한 격리 DB에서 실행한다. 환경 파일은 테스트 DB용으로 준비하고 접속 문자열·키·비밀번호를 결과에 붙이지 않는다.

```bash
# 읽기 전용: 테이블 생성/데이터 변경 없음
node --env-file=.env.local --import tsx scripts/migrate-customer-access.ts

# 명시 적용: SERIALIZABLE 트랜잭션 + 이관 도구 간 advisory lock
node --env-file=.env.local --import tsx scripts/migrate-customer-access.ts --apply
```

기본 명령은 기존 데이터 충돌만 검사한다. 이미 추가된 사용자/계정과의 충돌, DB 제약, 실제 생성 가능 여부는 적용 트랜잭션에서 검사한다. 실패하면 DDL과 데이터 변경을 함께 롤백한다. 출력은 건수와 검사 코드만 제공한다.

기존 쓰기 경로가 남아 있으므로 `bots.customer_id`는 이 단계에서 nullable이다. 신규 권한 함수는 연결되지 않은 봇을 거부한다. 기존 코드가 이관 후 만든 봇/계정은 인증 전환 직전 재이관하고 누락 0건을 검증해야 한다. 이관 도구의 advisory lock은 기존 앱 쓰기를 잠그지 않으므로 최종 전환 때는 쓰기 중지 구간이 필요하다.

기존 OAuth 연결만으로 검증된 이메일이라고 간주하지 않아 `email_verified_at`을 자동 채우지 않는다. Google 로그인 콜백의 검증된 클레임 확인과 이메일 검증 기반은 인증 전환 단계에서 연결한다.

운영 반영은 백업 → 쓰기 중지 → 사전 검사 → 이관 → 기존 봇/토큰/사용량 대조 → 전체 API 전환 → 세션 버전 변경 → 독립 QA 순서다. 이 단계만 적용한 후에는 기존 인증으로 동작한다. 사용자 로그인 전환 이후에는 기존 tenant 자격 증명으로 단순 롤백하지 않는다.

## 서버 접근 검사표

스키마에 새 열이 있는 것과 아래 기능의 권한 전환 완료는 다르다. 현재 모든 행은 **미전환**이다.

| 진입점 | 연결할 검사 |
| --- | --- |
| `/api/bots`, 봇 생성/삭제/이동 | 소유자, tenant 합산 플랜 한도, 봇/고객사 일치 |
| `/api/bots/[id]`, logo, support-status, proactive | 고객사 관리자 이상. 응답 필드 허용 목록으로 비밀값 제거 |
| docs, folders, qa, qa-folders, web-sources, generate-prompt | 해당 봇 고객사 권한, 하위 리소스 소속 확인 |
| logs, unanswered, qa-analytics, operations | 역할별 읽기/지식 수정 분리, 봇 고객사 범위 |
| `/api/support/handoffs` | 목록·단일 조회 범위 + 담당/상태/작성자 + 동시 처리 |
| 봇별 requests, 통합 `/requests` | 조회·상태·메모 동일 고객사 검사 |
| `/api/analytics`, 업무 홈·봇별 분석·테스트 | 서버 조회 범위와 역할 검사, 공개 채팅 API로 테스트 우회 방지 |
| tenants/settings, tenant/plan, integrations | 파트너 소유자만. 고객사 관리자/상담사에 비밀 토큰 미반환 |
| admin 화면/API | DB 플랫폼 관리자 확인. 고객사 전체 접근은 별도 권한 필요 |
| 모든 서버 페이지/액션 | 메뉴 숨김과 별개로 동일 권한 검사 |
| 공개 위젯/채팅/신청/외부 채널 | 기존 공개 봇 토큰·출처 정책 유지. 관리자 권한 부여 경로로 사용하지 않음 |

`resolveCustomerAccess`/`resolveBotAccess`는 전달받은 **서버 인증 사용자 ID**를 기준으로 DB 권한을 매번 읽는다. 클라이언트 user_id를 넘기면 안 된다. 변경 작업은 이 함수 호출만으로 동시 권한 회수/봇 이동 경합을 해결하지 않으므로, 실제 전환 단계에서 쓰기 쿼리의 권한 조건 또는 같은 트랜잭션의 잠금을 함께 구현한다.

## 검증 명령

```bash
node --import tsx --test tests/customer-access.test.ts
# 격리 임시 스키마에서 기존 최소 구조와 신규 구조를 만들고 전체 롤백
ACCESS_DB_CHECK=1 node --env-file=.env.local --import tsx tests/customer-access.integration.ts
npx tsc --noEmit
npx eslint lib/access scripts/migrate-customer-access.ts tests/customer-access.test.ts tests/customer-access.integration.ts
```

DB 통합 검증은 기존 테이블을 변경하지 않는다. 별도 무작위 스키마를 트랜잭션 안에서 생성하며 search_path를 그 스키마와 pg_catalog로만 제한한다. 스키마 생성 권한이 없으면 실패하며 이를 통과로 기록하지 않는다. `ACCESS_DB_CHECK=1`을 생략한 실행은 미실행이다.

전체 수동 인수 사례는 [HTML 체크리스트](qa/full-product-test-checklist.html)의 기획·예정 → 상담사 로그인·고객사 권한에 유지한다. 인증/API 전환 전에는 구현 완료 범위로 옮기지 않는다.

- 신규 역할·이관 사전 검사 단위 테스트 35개 통과.

- 기존 공개 토큰·tenant API 키·비밀번호 해시 보존, 이관 재실행, 역할 분리, 즉시 회수, 비활성 사용자/고객사 차단, 잘못된 고객사 연결 FK, 이메일 충돌 차단 확인.
- 운영 데이터 이관, 신규 로그인, 고객사/초대 화면의 수동 인수 테스트는 미실행.

### 연결 DB 읽기 전용 사전 검사

2026-10-21 검사에서 tenant 7개를 확인했고 `tenant_id`가 NULL인 봇 2개가 발견되어 적용 가능 판정은 **실패**했다. 정규화 이메일/OAuth 중복 검사에서는 차단 항목이 없었다. 이 두 봇의 상담 세션 수는 각각 0건이지만 문서·Q&A·기타 참조와 소유권을 확정한 것은 아니다.

소유자를 임의로 지정하거나 삭제하지 않았다. 실제 이관 전 해당 봇의 소유 관계와 데모 사용 여부를 확인한 후 처리해야 한다. 사전 검사의 실패 종료 코드는 의도한 적용 차단이며, 격리 스키마 자동 테스트 통과와 구분한다.

2026-10-21 후속: 사용자의 명시적 삭제 승인으로 위 소유자 없는 봇 2개와 연결된 Q&A 1개를 트랜잭션으로 삭제했다. 삭제 직전 두 봇의 `tenant_id IS NULL`을 잠금 상태에서 다시 확인했고 삭제 후 봇/Q&A 잔존 0건을 확인했다. 다시 실행한 읽기 전용 사전 검사는 tenant 7개, 차단 항목 0개로 통과했다. 실제 이관 적용은 아직 수행하지 않았다.
