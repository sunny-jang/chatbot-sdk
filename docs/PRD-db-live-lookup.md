# PRD — 실시간 조회 (대화 중 고객사 DB를 바로 확인)

작성일: 2026-10-27  
상태: 1단계 구현 대상. 2단계(본인 확인이 필요한 조회)는 이 문서의 범위 밖이다.  
연결: [DB 지식 연동](PRD-db-knowledge-source.md)(같은 데이터 연결·커넥터를 쓴다) · [데이터 비서](PRD-data-assistant.md) · [사용 시나리오](guides/db-knowledge-usage-scenarios.md)

## 1. 해결하려는 문제

DB 지식 연동은 표를 정해진 주기로 복사해 문서로 만든다. 메뉴·가격·지점처럼 자주 안 바뀌는 정보에는 맞지만, **재고·예약 잔여석·오늘 영업 여부처럼 지금 값이 중요한 정보**는 마지막 동기화 시점 값으로 답하게 된다.

목표는 **고객사가 미리 등록한 조회만, 대화 중에 그 자리에서 실행해 답하는 것**이다. 방문자 질문으로 AI가 SQL을 짜게 하지 않는다. 그리고 **한 번에 처리하기에 너무 넓은 요청은 실행하지 않고 "범위가 너무 넓어 답할 수 없다"고 안내**한다.

### 다루지 않는 것 (1단계)

- 개인정보가 걸린 조회("제 주문 어디쯤이에요?", "내 포인트") — 본인 확인 설계가 필요한 2단계
- 집계·통계·전체 목록("이번 달 매출 합계", "재고 전부 보여줘") — 실시간 조회로 하지 않는다. 범위가 너무 넓다고 안내
- 쓰기(예약하기·주문하기) — 범위 밖
- Gemini 모델 챗봇 — OpenAI 모델 챗봇에서만 동작(도구 호출 사용). 설정 화면에 안내

## 2. 제품 결정

| 항목 | 기본안 |
| --- | --- |
| 단위 | 챗봇 하나에 **실시간 조회** 최대 5개. 조회 하나 = 표 하나 + 조건 컬럼 + 보여줄 컬럼 |
| 만드는 방법 | 연결·표 선택 → 이름·설명("언제 쓰는지") → 조건 컬럼(방문자가 말해야 하는 값, 1~3개, 같음/포함) → 보여줄 컬럼(라벨·단위·값 바꾸기) → 고정 조건(선택) → 최대 결과 수 → 테스트 실행 → 저장. SQL 입력 화면 없음 |
| 실행 | 챗봇(OpenAI 도구 호출)이 질문에 맞는 조회를 고르고 조건 값을 채우면 서버가 미리 만든 질의에 값만 바인딩해 실행 |
| 안전 | 읽기 전용 트랜잭션, **5초 실행 제한**, 개인정보 추정 컬럼은 조건·보여줄 컬럼으로 고를 수 없음, 고객사 범위 격리(DB 지식과 동일) |
| 신선도 | 같은 조회·같은 값은 30초 동안 저장된 결과를 다시 쓴다. 답 아래 출처에 "실시간 조회 · 재고 조회 · 14:03 기준" |
| 요금제 | DB 지식과 같다(무료 불가, 그로스 이상) |
| 기록 | 실행마다 상태·결과 행 수·걸린 시간을 남긴다(방문자가 입력한 값은 저장하지 않음). 화면에 최근 7일 실행·실패·범위 초과 건수 |

## 3. 너무 넓은 요청 막기

방문자가 "재고 전부 알려줘", "지난 1년 주문 다 뽑아줘"처럼 처리량이 큰 요청을 하면 **실행하지 않고** 이렇게 답한다.

> 한 번에 확인하기엔 범위가 너무 넓어요. 상품명처럼 하나를 정해서 물어봐 주세요.

AI의 판단에만 맡기지 않고 서버가 단계마다 막는다.

| 번호 | 막는 곳 | 규칙 | 결과 상태 |
| --- | --- | --- | --- |
| G1 | 등록 | 조건 컬럼 1개 이상 필수. 조건 없는 "전체 조회"는 만들 수 없다 | 저장 거부 |
| G2 | 실행 전 | 필수 조건 값이 비어 있으면 실행하지 않는다 | `need_input` (무엇을 물어봐야 하는지 안내) |
| G3 | 실행 전 | 값이 `*`·`%`·`_`·"전체"·"모두"·"모든"·"전부"·"아무거나"·"all"이거나, 포함 검색 값이 2글자 미만이면 실행하지 않는다 | `too_broad` |
| G4 | 실행 | 결과를 최대 결과 수(1~10, 기본 5)+1행만 읽는다. 최대 결과 수를 넘으면 값을 돌려주지 않는다 | `too_broad` |
| G5 | 메시지 | 한 메시지에서 조회는 2번까지, 도구 호출 라운드는 1번. 넘는 호출은 실행하지 않는다 | `too_many_calls` |
| G6 | 대화·챗봇 | 대화 하나에서 10분에 10번, 챗봇 하나에서 1분에 60번까지 | `rate_limited` |
| G7 | 실행 | 5초 안에 끝나지 않으면 중단 | `timeout` |
| G8 | 질문 | "전부·모든·전체 목록·합계·평균·통계·순위·엑셀·다운로드·지난 N개월/년" 같은 대량 요청 표현이 있으면 그 메시지에서는 조회 도구를 주지 않고, 문서로 답할 수 없으면 범위가 너무 넓다고 안내 | 도구 미제공 |

`too_broad`·`too_many_calls`·`rate_limited`·`timeout`·`error` 결과에는 값이 없고 안내문만 있다. 시스템 지시로 "결과에 없는 숫자를 지어내지 말고 안내문대로 답하라"고 고정한다.

## 4. 주요 흐름

### 4.1 등록 (고객사 관리자 / 에이전시 담당자)

1. 챗봇 관리 → 지식 문서 탭 → **실시간 조회** 섹션 → 조회 추가.
2. 연결·표 선택(DB 지식과 같은 연결 목록).
3. 이름("재고 조회")과 설명("손님이 특정 메뉴의 남은 수량을 물을 때").
4. 조건 컬럼: 방문자가 말해야 하는 값. 예: `name` 같음(라벨 "메뉴 이름"), `size` 같음(선택 조건). 개인정보 추정 컬럼은 목록에서 막힌다.
5. 보여줄 컬럼: `stock`(라벨 "남은 수량", 단위 "개"), `is_open`(값 바꾸기 1=영업중). 개인정보 추정 컬럼은 막힌다.
6. 고정 조건(선택): `is_active 같음 1`.
7. 최대 결과 수(기본 5).
8. **테스트 실행**: 조건 값을 넣고 실행 → 결과 표 또는 "결과가 5건을 넘어 범위가 너무 넓어요" 같은 상태가 그대로 보인다.
9. 저장. 켜기/끄기, 수정, 삭제. 목록에 최근 7일 실행·범위 초과·실패 건수.

### 4.2 대화

1. 방문자: "아메리카노 지금 몇 잔 남았어요?"
2. 챗봇 서버가 켜진 조회를 도구로 붙여 모델을 호출 → 모델이 `재고 조회(메뉴 이름=아메리카노)`를 고른다.
3. 서버가 G2~G7을 검사하고 실행 → `{status:"ok", rows:[{메뉴 이름:"아메리카노", 남은 수량:"12개"}]}`.
4. 모델이 결과로 답: "지금 아메리카노는 12개 남았어요." 출처: "실시간 조회 · 재고 조회 · 14:03 기준".
5. "재고 전부 알려줘" → G8로 도구 미제공 → "한 번에 확인하기엔 범위가 너무 넓어요…".
6. "커피 재고" → 포함 검색 결과 7건 > 5 → G4 `too_broad` → 같은 안내 + 구체적인 이름을 물어본다.

## 5. 서버·데이터 설계

### 5.1 테이블

- `db_lookups`: id, bot_id, connection_id, name, description, schema_name, table_name, params(JSONB `[{column,label,match:"eq"|"contains",required,kind}]`), outputs(JSONB `[{column,label,unit,valueMap,type}]`), filters(JSONB, DB 지식 필터와 같은 모양), max_rows(1~10), enabled, created_by, created_at, updated_at. 삭제하면 행과 실행 기록을 함께 지운다.
- `db_lookup_calls`: id, lookup_id, bot_id, session_id, status(`ok`·`empty`·`need_input`·`too_broad`·`too_many_calls`·`rate_limited`·`timeout`·`error`), row_count, latency_ms, cached, created_at. 방문자가 입력한 값은 저장하지 않는다. 인덱스 (bot_id, created_at), (session_id, created_at).

### 5.2 커넥터

`Connector.lookup(config, query, { timeoutMs, limit })` 추가. Postgres는 읽기 전용 트랜잭션 안에서 `SET LOCAL statement_timeout`, MySQL은 세션 `MAX_EXECUTION_TIME`(MariaDB는 `max_statement_time`). 식별자 인용·값 바인딩·`LIMIT limit+1`. 포함 검색은 `ILIKE`/`LIKE`에 `%`·`_`를 이스케이프해 바인딩.

### 5.3 채팅

- OpenAI 모델이고 켜진 조회가 있으면 `tools`를 붙여 1차 호출 → `tool_calls`가 있으면 최대 2개 실행 → 결과를 붙여 2차 호출(도구 없음) → 최종 답.
- 문서 근거 없음으로 바로 거절하던 RAG 전용 모드도, 켜진 조회가 있으면 거절하지 않고 조회 기회를 준다.
- 분석 로그 `tool_name`: "실시간 조회(재고 조회)", 실패면 `tool_success=false`.

## 6. 인수 테스트

| 번호 | 시나리오 | 기대 |
| --- | --- | --- |
| L1 | 조건 컬럼 없이 저장 | 거부 (G1) |
| L2 | 개인정보 추정 컬럼을 조건·보여줄 컬럼으로 | 거부 |
| L3 | 테스트 실행 "아메리카노" | 결과 1행, 라벨·단위 적용 |
| L4 | 테스트 실행 포함 "커" (결과 6행, 최대 5) | `too_broad`, 값 없음 (G4) |
| L5 | 값 "전체" / "%" / 포함 1글자 | `too_broad` (G3) |
| L6 | 필수 조건 빈 값 | `need_input` (G2) |
| L7 | 한 메시지 도구 호출 3개 | 2개만 실행, 세 번째 `too_many_calls` (G5) |
| L8 | 대화에서 11번째 조회(10분 안) | `rate_limited` (G6) |
| L9 | 5초 넘는 질의 | `timeout`, 답에 숫자 없음 (G7) |
| L10 | "재고 전부 알려줘" | 도구 미제공, 범위가 넓다는 안내 (G8) |
| L11 | 다른 고객사 관리자가 조회 ID로 수정·테스트 | 404 |
| L12 | 실행 기록 | 상태·행 수·시간만, 방문자 입력값 없음 |
| L13 | 위젯 출처 | "실시간 조회 · 재고 조회 · HH:MM 기준" |
| L14 | 조회 끄기 | 대화에서 도구로 붙지 않음 |
| L15 | 무료 요금제 | 섹션에 안내, 추가 불가 |

## 7. 구현 순서

| 단계 | 내용 |
| --- | --- |
| A | `db_lookups`·`db_lookup_calls`, 커넥터 `lookup`, 검증(G1~G4·G8)·실행(G5~G7)·캐시, 관리 API(목록·추가·수정·삭제·테스트), 채팅 도구 호출, 위젯 출처 |
| B | 관리 화면(에이전시 챗봇 문서 화면·데스크 챗봇 작업공간), 최근 7일 집계, 사용 시나리오 문서 갱신 |
