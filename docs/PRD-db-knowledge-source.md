# PRD — DB 지식 연동 (고객사 데이터베이스를 챗봇 지식으로)

작성일: 2026-10-26  
상태: 제안 — 구현 전. 이 문서는 제품 기본안을 정한다. 운영에 제공되는 기능으로 안내하면 안 된다.  
연결: [데이터 비서](PRD-data-assistant.md)(같은 DB 연결을 공유) · [상담 담당자 로그인·고객사별 권한](PRD-agent-login-and-customer-access.md)

## 1. 해결하려는 문제

챗봇 지식은 지금 파일 업로드, URL 가져오기, 사이트 전체 가져오기로만 채운다. 홈페이지에 올라가지 않은 데이터 — 전체 상품·메뉴 목록, 가격·옵션, 지점 정보, 제품 스펙 — 는 고객사 DB에만 있어서 챗봇이 답하지 못하거나, 누군가 엑셀로 뽑아 문서로 올려야 한다. 그 데이터는 바뀌는데 문서는 안 바뀐다.

목표는 **고객사 DB의 테이블을 연결하면 행이 문서가 되어 챗봇이 답하고, 주기적으로 알아서 갱신되는 것**이다. 개발자 없이 설정할 수 있어야 하고, 읽기 전용이어야 하며, 고객사별로 격리되어야 한다. 범위는 DB 연동 하나로 좁힌다 — 엑셀·Google 시트·API는 이번 범위가 아니다(필요해지면 같은 구조 위에 추가).

### 다루지 않는 것

- 대화 중 실시간 조회("지금 재고 있어요?") — 데이터 비서 PRD의 3차
- 관리자용 집계 질문("오늘 대기 몇 건?") — 데이터 비서 PRD
- 엑셀·CSV·Google 시트·API 소스 — 후속

## 2. 제품 결정

| 항목 | 기본안 |
| --- | --- |
| DB 종류 | PostgreSQL, MySQL(MariaDB 포함). 이후 MSSQL |
| 연결 단위 | 고객사 1곳에 연결 N개. 연결은 고객사 관리자 또는 에이전시 소유자가 만든다 |
| 접속 정보 | 호스트·포트·DB명·사용자·비밀번호·SSL. `lib/crypto.ts`로 암호화 저장, 생성 후 비밀번호 재표시 없음 |
| 권한 | 읽기 전용 계정을 안내하고, 우리 쪽에서도 읽기 전용 트랜잭션·SELECT만 실행 |
| 가져오는 단위 | 테이블(또는 뷰) 하나 = 소스 하나. 행 하나 = 문서 하나 |
| 선택 | 테이블 체크 → 컬럼 역할(제목·본문·고유키·제외) → 필터(선택) → 폴더. SQL 입력 화면은 없다 |
| 문장 변환 | 행을 "라벨: 값" 줄로 바꿔 본문으로 저장. 컬럼 라벨과 단위는 설정에서 지정, AI가 초안 |
| 동기화 | 수동 / 매시간 / 매일 새벽(기본) / 매주. 고유키+해시로 변경분만 갱신, 사라진 행은 문서 보관(기본) 또는 삭제 |
| 한도 | 소스당 최대 5,000행(기본), 고객사당 연결 3개·소스 10개. 요금제별 조정 가능. 초과분은 가져오지 않고 안내 |
| 격리 | 연결·소스·문서는 고객사 범위에 묶인다. 다른 고객사·에이전시 집계 화면에서는 본문이 보이지 않는다(기존 정책) |
| 네트워크 | 공개 호스트만. 사설 IP·localhost 차단(웹 수집기 규칙 재사용). 우리 서버 고정 IP를 안내 |
| 실패 | 연결·동기화 실패는 소스 목록에 사유와 시각으로 표시. 연속 3회 실패 시 자동 동기화 중지 + 안내 |

## 3. 사용자와 역할

- **고객사 관리자**: 연결 생성·테스트, 테이블·컬럼 설정, 동기화 실행, 결과 확인. 자기 고객사만.
- **에이전시 소유자**: 담당 고객사에 대해 동일. 고객사 대신 설정해 줄 수 있다(접속 정보를 고객사 호스팅 업체에서 받아 입력).
- **상담 담당자**: 설정 불가. 챗봇 답변의 "출처 보기"에서 어떤 테이블의 행인지만 본다.
- **플랫폼 마스터**: 연결 수·동기화 건수·실패율. 접속 정보·데이터는 보지 않는다.

권한 키: 기존 `knowledge.manage`에 묶는다. 접속 정보 변경·삭제는 `settings.manage`.

## 4. 주요 흐름

### 4.1 연결 만들기 (개발자 없이)

1. 챗봇 → 문서 → "DB에서 가져오기" → "연결 추가".
2. DB 종류 선택. 접속 정보가 없으면 **연결 요청서** 내려받기: 필요한 권한(읽기 전용), 우리 서버 IP, 읽기 전용 계정 만드는 SQL 예시(Postgres·MySQL), 보낼 정보 항목. 호스팅 업체/개발사에 전달하고 받은 값을 입력한다.
3. "연결 테스트" → 성공하면 테이블 목록(이름, 행 수, 마지막 수정 추정)이 뜬다. 실패하면 원인을 사람 말로: "비밀번호가 틀렸어요", "방화벽에서 우리 IP(x.x.x.x)를 허용해주세요", "SSL이 필요한 서버예요".
4. 저장. 접속 정보는 암호화되어 저장되고 비밀번호는 다시 보이지 않는다(변경만 가능).

### 4.2 소스 만들기 (테이블 → 문서)

1. 테이블을 하나 고른다 → 상위 10행 미리보기.
2. AI가 컬럼 역할을 **제안**한다: 제목 컬럼(예: 상품명), 본문 컬럼(설명·가격·옵션), 고유키(id), 제외(내부코드·개인정보 추정). 사용자는 체크를 바꾼다.
3. 라벨·단위: 컬럼마다 챗봇이 읽을 라벨("가격", "원")을 AI 초안으로 채운다. 코드값(1=판매중)은 값 매핑을 입력할 수 있다.
4. 필터(선택): "판매중만" 같은 조건을 컬럼·값 선택 UI로. 숫자·날짜 비교, 포함/제외.
5. 폴더 선택, 동기화 주기 선택.
6. **답변 미리보기**: 변환된 문서 3개를 보여주고, 질문 3개(AI 제안 또는 직접 입력)에 실제로 답해 본다. 답이 이상하면 2~3번으로 돌아간다.
7. "가져오기 시작" → 진행률(N/M) → 결과(반영 N, 건너뜀 M, 실패 사유).

### 4.3 동기화

- 예약 시각에 `/api/cron/`에서 실행. 테이블을 고유키 순으로 읽어 행 해시를 비교: 새 행 → 문서 추가, 바뀐 행 → 본문·임베딩 갱신, 없어진 행 → 보관(검색 제외) 또는 삭제.
- 소스 목록에 "마지막 동기화 · 반영/갱신/제외 건수 · 다음 예정"을 보여준다. "지금 동기화" 버튼.
- 행 상한 초과 시 상한까지만 가져오고 "N행이 상한을 넘어 제외됐어요. 필터를 좁히거나 한도를 올려주세요"를 표시.

### 4.4 챗봇 답변

- 문서는 기존 검색(임베딩)에 그대로 들어간다. 본문은 "라벨: 값" 줄이라 "가격이 얼마예요?" 같은 질문에 값이 잡힌다.
- 가격·수량처럼 숫자 조건이 있는 질문("2만원 이하")을 위해 본문과 별도로 **숫자 필드**를 함께 저장하고, 검색 시 필드 필터를 먼저 건 뒤 임베딩으로 좁힌다(하이브리드). 1차는 숫자·날짜 두 종류.
- 답변의 "출처 보기"에 "달빛 카페 DB · menu 테이블 · 아메리카노" 형태로 표시. 행 원본 값은 관리자만 본다.
- 근거가 없으면 지어내지 않고 담당자 연결(기존 인계).

## 6. 서버·데이터 설계

### 6.1 테이블

- `data_connections` (id, customer_id, tenant_id, kind: postgres|mysql, host, port, database, username, secret_enc, ssl, status, last_tested_at, last_error, created_by, created_at) — 데이터 비서 PRD와 **공유**.
- `db_sources` (id, bot_id, connection_id, table_name, title_column, key_column, body_columns JSON[{column,label,unit,value_map}], excluded_columns, filter JSON, folder_id, schedule, row_limit, last_synced_at, last_result JSON, consecutive_failures, enabled)
- `db_source_rows` (source_id, row_key, row_hash, document_id, status: active|archived, synced_at) — 변경분 갱신·보관용
- `documents`에 `source_kind`(web|file|db)와 `numeric_fields JSON`(하이브리드 검색용) 추가. 기존 행은 null.
- 감사: `access_audit_logs`에 `data_connection.create/update/delete/test`, `db_source.create/update/delete/sync`

### 6.2 커넥터 인터페이스

```
testConnection(conn) → { ok, error?: 사람 말 메시지 }
listTables(conn)     → [{ name, rowEstimate, updatedAt? }]
sample(conn, table, limit=10) → { columns:[{name,type}], rows }
readRows(conn, source, cursor) → { rows, nextCursor }   // key 순, 배치 500행
```

Postgres는 `postgres.js`(이미 사용), MySQL은 `mysql2`. 모든 호출은 읽기 전용 세션(`SET TRANSACTION READ ONLY` / `SET SESSION TRANSACTION READ ONLY`), `statement_timeout` 20초, 연결당 풀 최대 2, 배치 500행, 소스당 행 상한.

### 6.3 안전

- 호스트는 DNS 해석 후 공개 주소만 허용(`lib/operations/web-fetch.ts`의 `publicAddress` 재사용). 포트는 1024~65535 허용(DB는 비표준 포트가 흔함) — 웹 수집기와 다름.
- 테이블·컬럼 이름은 서버가 식별자로 인용(쿼리 문자열 조립 금지), 필터 값은 바인딩.
- 개인정보 추정 컬럼(이름·전화·이메일·주소·주민번호·카드 패턴)은 기본 제외. 포함하려면 체크를 켜야 하고 경고를 띄운다.
- 접속 정보는 응답·로그·오류 메시지에 절대 포함하지 않는다. 연결 삭제 시 즉시 파기, 소스는 비활성.
- 동기화 작업은 고객사별 동시 1개, 전체 동시 N개(환경 변수).

### 6.4 비용

행 1개 = 임베딩 1회(변경 시에만). 소스당 5,000행 기본 상한, 요금제에 "DB 지식 행 수" 한도로 편입(기본안: 무료 불가, 그로스 10,000행, 프로 50,000행, 엔터프라이즈 협의).

## 7. 개발자 없이 설정 가능해야 한다

- SQL은 어디에도 보이지 않는다. 요청서의 "계정 만드는 예시"만 예외이며 호스팅 업체가 볼 용도다.
- 테이블 목록·미리보기·컬럼 역할·라벨은 모두 클릭과 AI 초안. 사용자는 틀린 것만 고친다.
- 연결 실패 메시지는 원인별 사람 말 + 할 일 한 줄.
- 답변 미리보기에서 바로 결과를 보고 되돌아갈 수 있다.

## 8. 구현 순서

1. **A**: `data_connections` + Postgres 커넥터(테스트·테이블·샘플) + 연결 UI + 요청서. 단위 테스트(공개 주소, 식별자 인용, 암호화 왕복).
2. **B**: `db_sources` + 컬럼 역할·라벨 UI + AI 초안 + 답변 미리보기 + 1회 가져오기(진행률). 기존 사이트 가져오기 UI 재사용.
3. **C**: 동기화(cron, 변경분, 보관/삭제, 실패 중지) + 소스 목록 상태 표시.
4. **D**: 하이브리드 검색(`numeric_fields`) + "출처 보기".
5. **E**: MySQL 커넥터, 요금제 한도, 마스터 집계.

각 단계는 독립 PR. 데이터 비서 PRD의 2차-A와 `data_connections`·연결 UI·요청서를 공유하므로 먼저 하는 쪽이 만든다.

## 10. 출시 기준과 남은 결정

출시 기준: C1~C12 통과, 커넥터 단위 테스트, 실제 고객사 1곳(후보: 모요)에서 테이블 1개 연동해 질문 20개 중 18개 이상 정답.

남은 결정:
- 사라진 행 기본 동작: 보관(기본안) vs 삭제
- 무료 요금제에서 DB 연동 허용 여부(기본안: 불가)
- 행 묶기(같은 카테고리 N행을 문서 하나로) 1차 포함 여부
- 요청서 형식(PDF vs 링크 공유 페이지)
