# PRD — 상담 담당자 로그인·고객사별 권한

작성일: 2026-10-21  
상태: 고객사 상담 포털 일부 로컬 구현 — 관리자 기능·공통 신원 전환·전체 인수·운영 이관 미완료
연결: [운영 화면 개편](PRD-workspace-redesign.md) · [1차 화면 PR #1](https://github.com/sunny-jang/chatbot-sdk/pull/1)

구현 현황·이관 절차·API 전환 목록: [구현 기록](implementation-agent-access.md). 기존 인증을 유지한 채 데이터 기반부터 추가하며, 모든 권한 전환이 끝나기 전 신규 상담사 로그인을 활성화하지 않는다.

## 1. 해결하려는 문제

현재는 로그인 계정과 작업 공간이 `tenants` 한 행에 함께 저장되어 있다. `/support`는 기존 관리자 계정으로 사용하는 상담함이며, 상담 담당자별 로그인이나 고객사별 권한은 없다. 에이전시가 고객사에 계정을 넘기면 다른 고객사의 대화·챗봇·키에 접근하지 못하도록 분리할 수 없다.

목표는 **에이전시는 고객사 여러 곳을 관리하고, 고객사 담당자는 자신의 회사 상담만 처리하는 구조**다. 작은 사업장은 사장님 한 명이 관리자와 상담 담당자를 겸한다. 불필요한 조직도·부서·복잡한 승인 절차는 넣지 않는다.

## 2. 제품 결정

| 항목                 | MVP 기본안                                                                           |
| -------------------- | ------------------------------------------------------------------------------------ |
| 일반 회원가입        | 개인 사용자와 파트너 작업 공간 1개를 생성하고 가입자를 소유자로 지정                 |

| 자사 사용            | 기본 고객사 `우리 회사`를 자동 생성해 동일한 구조 사용                               |
| 상담 담당자          | 고객사에 초대되어 자기 계정으로 로그인. 배정된 고객사 범위만 접근                    |
| 로그인 방식          | 기존 이메일/비밀번호와 Google 로그인을 공통 로그인으로 유지                          |
| 초대 전달            | MVP는 복사 가능한 링크. 자동 이메일 발송은 후속 범위                                 |

| 담당 범위            | MVP는 고객사 단위. 해당 고객사의 모든 챗봇 상담을 처리. 챗봇별 세부 배정은 후속      |
| 요금                 | 기존 봇 수·월 대화 세션 한도 유지. 좌석 과금·고객사 수 과금은 이번에 도입하지 않음   |
| 독립 사업장          | 고객사 관리자 한 명이 상담까지 처리. 추가 상담사 계정은 선택                         |

이 문서는 제품 기본안을 정한다. 운영에 이미 제공되는 기능으로 안내하면 안 된다.

## 3. 사용자와 역할

### 플랫폼 마스터

파트너 계정·구독 상태·플랜·서비스 운영을 관리한다. 일반 파트너 가입으로 생성되지 않는다. 기존 관리자 판정을 명시적인 플랫폼 권한으로 이관한다. 고객 상담 원문에 대한 자동적인 전체 접근은 부여하지 않는다. 대리 로그인과 고객 계정으로 가장하는 기능은 MVP에 포함하지 않는다.

### 파트너 소유자

에이전시 또는 직접 사용하는 사업장 대표다. 고객사 생성, 챗봇 연결, 고객사 관리자·담당자 초대, 고객사별 운영 확인, 작업 공간 키·연동·요금제를 관리한다. 작업 공간 전체를 관리할 수 있지만 다른 파트너 공간에 대한 권한은 없다.

### 고객사 관리자

고객사 대표 또는 관리 담당자다. 자기 고객사의 상담·접수와 챗봇의 지식·응대 설정을 관리하고 상담 담당자를 초대한다. 파트너의 결제·API 키·다른 고객사 목록에는 접근할 수 없다. 직접 상담 답변도 가능하다.

### 상담 담당자

자기 고객사의 대화·인계 요약·문의·견적을 확인하고 상담 시작·답변·종료, 접수 상태 변경과 내부 메모를 수행한다. 봇 삭제·지식 수정·키·결제·구성원 관리에는 접근하지 않는다.

한 사용자가 A 고객사의 관리자이고 B 고객사의 상담 담당자일 수 있다. 권한은 선택한 고객사와 멤버십에서 계산한다. 다른 공간의 높은 역할이 현재 고객사에 전파되지 않는다.

## 4. 권한표

`자기 고객사`는 활성 멤버십이 있는 선택한 고객사만 의미한다. 마스터의 플랫폼 운영 권한은 이 표의 사업장 권한과 별개다.

| ---------------------------------------- | ----------------------- | ----------------------- | ----------------------- |
| 파트너 내부 고객사 목록·생성             | 전체                    | 불가                    | 불가                    |
| 고객사 정보 조회                         | 전체                    | 자기 고객사             | 자기 고객사 표시용 정보 |
| 고객사 정보 수정                         | 전체                    | 자기 고객사             | 불가                    |
| 대화·인계 요약 조회(상담 업무)           | 전체                    | 자기 고객사             | 자기 고객사             |
| 대화 원문 분석·대화 기록·세션 상세       | 자사·미배정 봇만        | 자기 고객사             | 불가                    |
| 상담 시작·답변·종료                      | 전체                    | 자기 고객사             | 자기 고객사             |

| 미응답 질문 보완(원문 열람·Q&A 추가)     | 자사·미배정 봇만        | 자기 고객사             | 불가                    |
| 챗봇 지식·Q&A·응대 설정·테스트           | 전체                    | 자기 고객사             | 불가                    |
| 챗봇 생성·삭제·고객사 간 이동            | 가능                    | 불가                    | 불가                    |
| 설치 코드·공개 위젯 토큰 조회            | 가능                    | 자기 고객사             | 불가                    |
| 고객사 관리자 초대·역할 부여             | 가능                    | 불가                    | 불가                    |

| 자신/동료를 관리자·소유자로 승격         | 소유자 정책으로만       | 불가                    | 불가                    |
| 결제·전체 사용량·API 키·외부 연동 비밀값 | 가능                    | 불가                    | 불가                    |
| 고객사 범위의 운영 통계(집계)            | 전체                    | 자기 고객사             | MVP는 상담 업무 수치만  |
| 전체 내보내기·대량 삭제                  | 이번 MVP 신규 제공 없음 | 이번 MVP 신규 제공 없음 | 불가                    |

고객사 관리자는 자신과 다른 고객사 관리자를 해제할 수 없다. 소유자만 처리한다.

2026-10-23 결정: 고객사에 배정된 챗봇의 **대화 원문·대화 기록·세션 상세·거절 문장**은 고객사 데이터다. 에이전시 분석 대시보드(`/analytics`, `/bots/[id]/analytics`, `/bots/[id]/logs`)는 해당 봇에 대해 세션·메시지·토큰·거절률 같은 집계만 보여주고 원문은 desk의 고객사 관리자만 본다. 에이전시 자기 사업장(기본 고객사 `우리 회사`) 봇과 아직 고객사에 배정되지 않은 봇은 예외다. 상담함에서 담당자 연결로 넘어온 대화는 상담 업무이므로 이 제한의 대상이 아니다. 같은 날 추가 결정: **문의·견적 접수와 미응답 질문 보완도 고객사가 직접 처리**한다. 에이전시 `/requests`·업무 홈 접수 지표는 자사·미배정 봇만 세고, 고객사 봇의 `/api/bots/[id]/requests`·`/api/bots/[id]/unanswered`는 403이다. 소유자 이전·파트너 공동 관리자 기능은 후속으로 둔다.

## 5. 주요 흐름

### 5.1 파트너의 첫 사용

1. 일반 회원가입 완료.
2. 사용자·파트너 작업 공간·소유자 멤버십·기본 고객사를 한 번만 생성.
3. `/`에서 업무 홈 진입. 기본 고객사 이름을 실제 상호로 바꿀 수 있음.
4. 챗봇을 만들고 고객사를 연결한 뒤 설치.
5. 추가 고객사가 있으면 고객사 관리에서 생성하고 봇을 연결.

Google 로그인 재시도나 요청 중복으로 작업 공간을 중복 생성하지 않는다.

### 5.2 고객사 담당자 초대

1. 파트너가 고객사를 선택해 이름·이메일·역할을 입력.
2. 고객사 관리자는 자기 고객사의 `상담 담당자`만 초대 가능.
3. 시스템이 만료 시간이 있는 초대 링크를 생성하고 복사 버튼 제공.
4. 초대받은 사람은 링크에서 고객사명·초대 역할·초대한 파트너를 확인.
5. 기존 계정은 로그인하고, 신규 사용자는 초대 가입을 진행.
6. 로그인 사용자의 검증된 이메일과 초대 이메일이 같아야 수락.
7. 수락과 멤버십 생성을 트랜잭션으로 처리하고 초대를 사용 완료로 변경.
8. 고객사 관리자·상담 담당자는 `/support`로 이동. 설정 업무는 메뉴에서 선택.

잘못된 이메일로 로그인했으면 계정을 바꿀 수 있다. 다른 이메일로 초대를 넘겨 수락하는 기능은 제공하지 않는다. 이메일 문자열이 같다는 이유만으로 검증되지 않은 OAuth 계정을 기존 사용자에게 자동 연결하지 않는다.

### 5.3 매일 상담하기

1. `/login` 또는 안내용 `/support/login`으로 접근.
2. 공통 로그인 후 접근 가능한 고객사가 하나면 자동 선택, 여러 곳이면 선택.
3. 대기 상담을 선택하고 대화·AI 인계 요약을 읽음.
4. `상담 시작` 시 현재 사용자 ID와 표시 이름을 담당자로 기록.
5. 답변과 접수 상태 변경을 수행하고 필요 시 상담 종료.
6. 활동 기록에 행위자와 대상 고객사·세션을 남김.

상담 기록의 작성자 이름을 사용자가 요청 본문에 임의로 넣지 못하게 한다. 현재의 `agentName = 관리자` 방식은 로그인 사용자 정보로 대체한다.

### 5.4 작은 사업장

소유자 또는 고객사 관리자 한 계정으로 지식 수정과 상담을 모두 사용한다. 별도 담당자를 만들도록 강제하지 않는다. 부서·직급·다단계 결재를 입력하지 않아도 시작할 수 있다.

### 5.5 퇴사·권한 회수

멤버십 해제/역할 변경 즉시 다음 API 요청부터 새 권한을 적용한다. 이미 열린 상담함도 권한 없음 상태로 전환하고 폴링을 중단한다. 작성 중인 초안은 다른 고객사에 전송하지 않는다. 미전송 초안의 저장·복구는 같은 사용자·고객사·세션 범위로 한정한다.

퇴사자의 과거 메시지와 이력은 유지한다. 진행 상담의 담당자는 미배정으로 전환하되 기존 답변 작성자 이력은 바꾸지 않는다. 사용자 자체 삭제가 모든 회사의 기록을 지우지 않는다.

## 6. 화면과 URL (구현 목표)

| 화면               | 경로                                    | 접근                                       |
| ------------------ | --------------------------------------- | ------------------------------------------ |
| 공통 로그인        | `/login`                                | 전체                                       |
| 상담용 로그인 진입 | `/support/login`                        | 공통 로그인으로 연결하며 상담 목적지 유지  |
| 마스터 어드민      | `/admin`                                | 플랫폼 마스터                              |

| 구성원·초대        | `/customers/[customerId]/members`       | 소유자·해당 고객사 관리자                  |
| 초대 확인·수락     | `/invite/[token]`                       | 유효 초대와 본인 확인 필요                 |
| 고객사 선택        | `/workspaces/select`                    | 활성 멤버십이 여러 개인 사용자             |
| 상담 업무          | `/support`                              | 선택 고객사에 상담 권한이 있는 사용자      |
| 문의·견적          | `/requests`                             | 선택 고객사에 접수 권한이 있는 사용자      |
| 챗봇 관리          | 기존 `/bots` 및 하위 URL                | 소유자·해당 고객사 관리자                  |

상담사마다 다른 로그인 시스템을 만들지 않는다. URL은 진입점이고 권한은 서버가 검증한다. 상담 담당자가 루트로 들어오면 상담함으로, 소유자는 업무 홈으로 안내한다. 권한 없는 화면을 단순 숨기는 것으로 접근을 허용하지 않는다.

이 표의 신규 경로는 **설계 경로**다. 지금 접속 가능한 기능이라고 안내하지 않는다. 비로그인 사용자의 목적지는 로그인 후에도 유지하되 외부 URL·다른 고객사로 우회하는 리디렉션은 허용하지 않는다.

## 7. 서버·데이터 설계

### 현재 코드에서 바뀌어야 하는 지점

- `auth.ts`: 현재 로그인 사용자의 ID가 `tenants.id`다. 사용자 ID와 작업 공간 ID를 분리.
- `lib/auth.ts`: 단순 `getTenantId()` 반환에 의존하는 API를 사용자·고객사·역할 접근 검사로 전환.
- `bots.tenant_id`, `chat_sessions.tenant_id`, `customer_requests.tenant_id`는 소유 파트너와 과금 범위로 유지.
- 상담 답변 API·상태 변경 API: `assigned_agent_user_id`와 실제 작성 사용자 ID를 서버에서 기록.
- 미들웨어의 로그인 검사는 1차 검사일 뿐, 페이지·서버 액션·API·파일 접근에서도 대상별 권한 검사.

### 접근 범위 계산

서버가 로그인 사용자와 DB의 활성 멤버십으로 `userId / tenantId / customerId / permissions`를 구성한다. 클라이언트가 보낸 tenant_id·customer_id는 선택 요청일 뿐 권한 증명이 아니다.

- 파트너 소유자: 자기 파트너 공간 전체 또는 선택한 고객사.
- 고객사 관리자·담당자: 자신에게 허용된 고객사만.
- 봇 → 고객사 → 파트너 소유 관계까지 검증한 후 대화·메시지·신청 조회.
- 캐시·조회 키에 사용자와 고객사 범위를 포함. 고객사 전환 시 이전 요청 취소·화면 데이터 초기화.
- 세션/JWT에 기록된 역할만 신뢰하지 않고 요청 시 DB의 최신 활성 권한을 확인.
- 내부 API는 401(비로그인), 403(허용되지 않는 기능), 404(접근할 수 없는 대상)를 일관되게 사용. 다른 고객사의 존재·이메일을 응답에 노출하지 않음.
- 기존 공개 위젯 API는 고객용 공개 경로로 유지. 상담 담당자의 관리자 로그인 권한과 혼합하지 않음.

### 변경 대상 API군과 완료 조건

상담·메시지·문의·메모만 변경하고 끝내지 않는다. 다음 모든 진입점을 목록화한 접근 검사표를 구현 PR에 포함한다.

1. 봇 목록/상세/생성/수정/삭제 및 설치 토큰.
2. 문서·폴더·Q&A·URL 수집·테스트·프롬프트 생성.
3. 상담 목록·단일 메시지·상태·답변·담당자 배정.
4. 견적·상담 신청·메모·상태·향후 내보내기.
5. 고객사 통계·대화 기록·미응답 보완.
6. 파트너 키·외부 연동·전체 요금/사용량·관리자 API.
7. 미리보기·테스트 토큰·파일·연동 채널처럼 우회 접근이 가능한 경로.

채널의 외부 봇 토큰·서명 비밀값은 상담 담당자·고객사 관리자 응답에 포함하지 않는다. 이미 설정된 외부 연동으로 들어오는 답변도 정확한 봇/고객사에 연결한다.

## 8. 초대·세션 상세 정책

- 기본 초대 만료: 72시간. 링크에는 충분한 난수 토큰 사용, DB에는 해시만 저장.
- 상태: pending → accepted / revoked / expired. 만료는 서버 현재 시각으로 판정.
- 동일 사용자·고객사 멤버십은 중복 생성하지 않음. 동시 수락은 같은 결과를 반환.
- 재초대 시 기존 미수락 링크 무효화. 해제된 사용자를 복귀시키려면 새 초대가 필요.
- 링크를 열거나 미리보기 크롤러가 GET으로 접근한 것만으로 수락하지 않음. 명시적 POST 수락 필요.
- 초대 수락·취소·역할 변경은 인증·대상 권한·요청 출처를 검증하고 요청 빈도 제한 적용.
- 초대 원문 토큰·비밀번호·OAuth 비밀값은 운영 로그·감사 로그에 저장하지 않음.
- 초대 확인 전에는 고객사명·역할 등 최소 정보만 표시. 다른 멤버와 대화 정보는 미노출.
- 멤버십 회수 시 전체 로그아웃을 강제하기보다 해당 고객사 접근부터 차단. 다른 활성 공간은 계속 사용 가능.
- 이메일/비밀번호 가입자는 서버가 발송한 일회성 이메일 확인 링크로 이메일을 검증한 뒤 초대를 수락한다. 이메일 확인·비밀번호 재설정 메일 발송은 MVP 필수 기반이며, 초대 메일 자동 발송을 후속으로 둔 것과 구분한다.
- 메일 발송 설정이 없는 환경에서는 이메일 미검증 계정의 초대 수락을 차단한다. 검증된 Google 계정으로 수락하는 경로는 제공하되 미검증 주소와 자동 병합하지 않는다. 발송 서비스·발신 도메인 설정과 재설정 토큰 만료·단일 사용 검증은 구현 착수 시 환경 작업 목록에 포함한다.
- 비밀번호 재설정은 계정 존재 여부를 외부에 구분해 응답하지 않는다. 초대 가입이 기존 자격 증명을 덮어쓰지 않게 한다.

## 9. 상담 담당과 동시 처리

담당자는 우선 1명이다. 배정은 대기 → 진행 상태 변경과 함께 원자적으로 처리한다. 동시에 두 명이 시작하면 먼저 성공한 담당자를 표시하고 두 번째 사람에게 이미 시작되었다고 안내한다. 다른 담당자의 상담 조회는 고객사 권한 안에서 가능하지만, 담당자 변경은 명시적 인계 동작으로 기록한다.

전송 시 현재 담당/상태를 서버에서 재검사하고 중복 제출 방지 키를 사용한다. 종료된 상담을 늦은 전송 요청이 다시 열지 못하게 한다. 고객사 관리자는 자기 고객사의 담당을 변경할 수 있고, 일반 담당자는 미배정 상담 수락과 자신이 맡은 상담 전송/종료를 수행한다. 다른 담당자의 상담에 답하려면 먼저 인계를 받는다.

안 읽음·실시간·첨부 개선은 별도 위젯 개선 계획과 연결하되 로그인 MVP 완료 조건에 전부 묶지는 않는다. 이후 첨부 다운로드에도 동일 고객사/담당 권한을 적용한다.

## 10. 기존 데이터·요금제 이관

1. 현행 tenant·봇·대화·API 키 관계와 이메일 충돌을 사전 점검하고 백업/복구 절차를 준비.
2. users·멤버십·고객사 테이블을 먼저 추가. 기존 tenant ID를 파트너 공간 ID로 그대로 유지.
3. 기존 tenant마다 소유자 user와 기본 고객사를 만들고 해당 tenant의 봇을 기본 고객사에 연결.
4. 기존 비밀번호 해시는 같은 알고리즘으로 복사하며 평문 비밀번호는 취급하지 않음. OAuth 연결은 기존 provider/subject를 이관.
5. 봇 ID·공개 위젯 토큰·설치 스크립트 URL·문서/대화 연결은 변경하지 않음.
6. 기존 API 키와 결제·사용량은 tenant에 유지. customer_id로 과금 주체를 바꾸지 않음.
7. 이관 검증 후 인증 버전을 전환하고 한 번 재로그인을 안내. 구 tenant_id를 user_id로 간주하는 기존 토큰을 무기한 호환하지 않음.
8. 인증 전환 전에는 스키마를 추가한 상태로 이전 코드 복귀 가능. 전환 후 새 사용자·멤버십이 생성된 상태에서는 구 코드로 단순 롤백하지 않고 신 인증을 유지하거나 검증된 역이관 절차를 사용.

현재 코드의 무료(봇 1개·월 1,000세션), 그로스(3개·5,000세션), 프로(5개·10,000세션), 엔터프라이즈 협의 한도를 유지한다. 고객사에 봇을 옮기거나 담당자가 추가되어도 한도를 우회하거나 같은 대화를 중복 과금하지 않는다. 신규 좌석 가격/요금제 변경은 별도 결정이다.

이관 후 모든 기존 봇의 고객사 연결이 유효한지 확인한 뒤 필수 제약을 적용한다. 연결이 없는 봇을 임의의 고객사에 노출하지 않는다. 고객사 삭제는 MVP에서는 활성 멤버·봇·미완료 상담이 있으면 막고, 비활성화부터 지원한다.

## 11. 구현 순서

| 단계              | 결과물                                                 | 통과 조건                                            |
| ----------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 1. 신원·이관 기반 | 사용자/공간 분리, 고객사·멤버십, 기존 데이터 이관 도구 | 기존 봇·설치 유지, 로그인/이메일 충돌·멱등 이관 검증 |
| 2. 서버 권한 전환 | 공통 접근 검사, 모든 관리자 API 적용                   | 타 고객사 ID 교체·직접 URL·취소 권한 차단            |

| L17 | 모바일·접근성                                        | 로그인·고객사 선택·초대·상담 업무를 키보드와 모바일로 완료 가능     |
| L18 | 이관 도중 실패·이관 재실행·전환 전후 복구            | 중복 사용자/고객사 없이 일관성 유지, 복구 후 접근 범위 유지         |

## 13. 출시 기준과 남은 결정

필수 출시 기준은 서버 권한 검사표, 이관 리허설/복구 확인, 인수 테스트, 기존 1차 화면 회귀의 통과다. 성공 지표는 초대 수락→첫 상담 응대까지의 완료율·소요 시간과 로그인/권한 오류율을 기록하고 초기 운영 후 목표치를 확정한다. 다른 고객사 데이터 노출은 허용하지 않는다.

자동 이메일 초대, 공동 파트너 관리자, 세부 봇별 배정, SSO·부서 관리, 상담사 좌석 과금, 대리 로그인은 후속 범위다. 이 PRD의 초대 72시간·고객사 단위 배정·소유자 한 명 정책은 구현 기본안이며 변경 시 권한표와 인수 테스트도 함께 수정한다.


## 2026-10-22 구현 추가

에이전시와 고객사의 상담 진입점을 분리한다. 고객사 포털은 공통 `desk` 서브도메인을 사용하고 로그인 후 허용된 고객사만 표시한다. 고객사별 서브도메인은 이번 범위에 포함하지 않는다. 실제 구현 및 검증·운영 설정 상태는 [구현 기록](implementation-agent-access.md)을 따른다.


## 2026-10-22 진입점 변경과 인수 상태

사용자 확정에 따라 에이전시 `/login`과 공통 `desk.서비스도메인`의 상담 로그인 진입점을 분리한다. 상담 담당자별로 별도 주소를 만들지 않는다. desk 호스트 `/login`은 고객사 로그인으로 연결되고, 내부 경로는 `/customer/login`, `/customer`, `/customer/[customerId]/support`, `/requests` 대신 `/customer/[customerId]/requests`, `/customer/[customerId]/members`를 사용한다. 초대는 `/customer/invite/[token]`, 이메일 확인은 `/customer/activate/[token]`이다. 위 6장의 공통 로그인·URL 표는 최초 설계이며 이 진입점 결정으로 대체한다. Google과 사용자 신원 공통화 요구까지 완료된 것은 아니다.

[PRD 대비 구현 검수](reviews/prd-implementation-audit-2026-10-22.md)에 L01~L18의 부분 구현·미충족과 코드 근거를 기록한다. 고객사 관리자 지식·응대 설정 등 필수 범위를 구현 없이 완료 처리하지 않는다.
