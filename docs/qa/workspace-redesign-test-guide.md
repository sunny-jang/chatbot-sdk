## 1. 이번 테스트 범위

| 포함                                              | 아직 미구현·이번 합격 기준에서 제외 |
| ------------------------------------------------- | ----------------------------------- |
| 업무 홈, 상담함, 통합 문의·견적, 챗봇 목록 분리   | 상담사별 계정·초대·로그인           |
| 업무/관리/도움말 메뉴와 모바일 화면               | 고객사별 담당자·역할 권한           |
| 상담 필터·검색·답변 초안·폴링·오류 처리           | 파트너의 여러 고객사 관리           |
| 기존 tenant(가입 계정의 작업 공간) 간 데이터 격리 | 새 요금제 정책·고객사 데모          |

현재는 **가입 계정 하나가 작업 공간 하나**다. 같은 고객사의 상담사 두 명을 초대하는 흐름은 구현되지 않았다. 메뉴에 항목이 보이는지와 서버의 데이터 접근 검사는 별도로 확인한다. 운영 서비스에 합쳐진 상태가 아니라 Draft PR 검토 단계다.

## 2. 실행 준비

### 코드와 환경

```bash
git fetch origin
git switch codex/workspace-redesign
# 로컬 브랜치가 없으면: git switch --track origin/codex/workspace-redesign
git pull --ff-only
npm ci
```

저장소 루트에 테스트 환경용 `.env.local`을 준비한다. 실제 키는 환경 담당자에게 별도로 전달받으며 문서·이슈·스크린샷에 붙이지 않는다.

| 환경변수                                   | 용도                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| `POSTGRES_URL`                             | SSL 접속 가능한 격리된 테스트 DB                                         |
| `AUTH_SECRET`                              | 로그인 세션 암호화용 고정된 테스트 환경 비밀값                           |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google 로그인 검증 시 필요. 테스트 도메인의 OAuth 콜백 설정도 필요       |
| `ADMIN_EMAILS`                             | 마스터 메뉴·API를 확인할 테스트 관리자 이메일. 일반 계정은 포함하지 않음 |

실제 AI 답변 생성은 테스트 tenant의 모델 API 키가 있어야 한다. 목록·필터·메뉴·빈 상태 테스트에는 모델 호출이 필요하지 않다.

```bash
npm run dev -- --port 3002
```

[로그인](http://localhost:3002/login)에서 시작한다. **localhost는 해당 개발자의 PC**다. 다른 PC에서 기존 사용자의 `localhost:3002`로 접속해도 같은 서버가 열리지 않는다. 각자 실행하거나 팀에서 제공하는 테스트 배포 URL을 사용한다. 테스트 배포 URL은 PR의 실제 배포 링크를 확인한다.

### 로그인 주의

- 개발 모드에서만 `테스트로 넘어가기 →` 버튼이 나타난다.
- 이 버튼은 DB에서 가장 먼저 만들어진 tenant로 로그인한다. 두 번째 독립 계정을 만드는 버튼이 아니다.
- 데이터 격리는 일반 이메일/Google 로그인으로 **서로 다른 두 테스트 계정**을 준비해 확인한다.
- 개발 로그인 후 첫 이동은 기존 `/analytics`일 수 있다. 새 화면 확인은 메뉴의 **업무 홈** 또는 `/`로 이동한다.
- 첫 로그인·화면 로딩은 기존 스키마 초기화 때문에 지연될 수 있다. 실패하면 서버 로그와 DB 연결을 확인한다.
- `npm run build` + `npm run start -- --port 3002`로 확인할 때는 개발 로그인 버튼이 없다. 일반 테스트 계정이 필요하다.

### 수동 테스트 데이터

UI의 생성·전송·상태 변경은 실제 DB에 저장된다. **격리된 테스트 DB와 테스트용 고객 위젯에서만** 아래 데이터를 준비한다.

| 데이터             | 준비 방법                                                                                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 계정 A, 계정 B     | 서로 다른 가입 계정으로 준비. 각자 소유 봇 생성                                                                                                            |
| 대기 상담 2건 이상 | A의 봇 설정에서 `챗봇 + 상담원 연결`, 채널 `자체 상담함만`, 운영 가능 시간·강제 무인 설정 확인. 서로 다른 테스트 브라우저 세션의 위젯에서 담당자 연결 요청 |
| 진행·종료 상담     | 테스트 상담을 시작/종료해 상태별 데이터 준비                                                                                                               |
| 긴 대화            | 테스트 위젯과 상담함에서 스크롤이 생길 만큼 메시지 교환                                                                                                    |
| 문의·견적          | 봇의 `견적·상담 신청`에서 폼 활성화 후 테스트 정보로 접수. 신규·처리 중·완료 상태를 준비                                                                   |
| 데이터 없는 공간   | 별도 신규 테스트 계정으로 빈 상태 확인                                                                                                                     |

실제 고객의 상담을 시작/종료하거나 답변을 전송하지 않는다. Slack·Telegram 외부 연동을 켜면 테스트 답변도 외부 채널로 전달될 수 있으므로 이 가이드의 기본 검증은 `자체 상담함만`을 사용한다.

아래 DB 자동 검증은 데이터를 롤백하므로 **브라우저에 남는 샘플을 생성하지 않는다.**

## 3. 빠른 확인 (약 10분, 데이터 준비 시간 제외)

1. 로그인 후 `/`에서 실제 업무 수치와 빈 상태/대기 목록이 보이는지 확인.
2. **진행 중인 상담** 수치를 눌러 상담함의 `상담 중` 필터가 선택되는지 확인.
3. 상담 A에서 초안 입력 → 상담 B로 이동 → A로 돌아와 초안 확인.
4. 테스트 상담에 답변 1회 전송 → 위젯과 상담함에 각각 1회 표시되는지 확인.
5. `/requests`에서 상태 필터·이름/내용 검색 → 해당 봇의 신청 관리로 이동.
6. `/bots`에서 기존 설정·문서·테스트·대화 기록 화면 접근.
7. 화면 너비 390px에서 메뉴 열기/닫기와 상담 목록/대화 전환.
8. 로그아웃 상태에서 `/support`, `/requests` 및 상담 API 접근 차단 확인.

빠른 확인만으로 전체 승인하지 말고 아래 오류·동시 처리·격리 시나리오까지 기록한다.

| S11 | 종료한 상담 확인                                                    | 답변 입력 불가, 시작/종료 재실행 버튼 비활성. 중복 안내가 추가되지 않음                                                        |
| S12 | 테스트 위젯 ↔ 상담함에서 답변 왕복                                 | 고객/AI/담당자 표시와 메시지 내용 일치. 답변 1회가 중복 저장되지 않음                                                          |

S06은 브라우저 전체 오프라인만으로는 부족하다. 전송은 실패하고 목록 GET은 성공하는 조건을 만들어야 오류 상태 분리를 검증할 수 있다. S08은 요청·응답 순서를 Network 기록과 함께 남긴다. 폴링은 요청 완료 후 다음 조회를 예약하므로 느린 응답 중 동일 폴링이 중첩되지 않아야 한다.

| M02 | 모바일에서 상담 선택 → 목록으로                                  | 목록/대화 전환 가능. 초안 유지                                                |
| M03 | 키보드 Tab·Enter로 메뉴·필터·전송 접근                           | 포커스 표시와 본문 바로가기 동작. textarea Enter는 줄바꿈, 전송 버튼으로 제출 |

개별 메시지 조회와 목록 조회는 API 인자가 다르다.

```text
GET /api/support/handoffs?sessionId=<선택한 상담 세션 ID>
GET /api/support/handoffs?status=waiting&q=<검색어>&selectedSession=<상세에 유지할 세션 ID>
```

## 5. 자동 검증 명령

루트 디렉터리에서 실행한다.

```bash
# DB가 필요 없는 기존·신규 회귀 테스트: 현재 기준 72개
node --import tsx --test tests/operations.test.ts tests/proactive.test.ts tests/proactive-ai.test.ts tests/workspace-inbox.test.ts

# 타입 검사
npx tsc --noEmit

# 이번 개편 파일의 린트
npx eslint app/Sidebar.tsx app/layout.tsx app/page.tsx app/bots/page.tsx app/requests/page.tsx app/support/page.tsx app/support/SupportInbox.tsx app/loading.tsx app/api/support/handoffs/route.ts lib/workspace-inbox.ts lib/support-inbox-query.ts tests/workspace-inbox.test.ts tests/workspace-inbox.integration.ts

# 프로덕션 빌드
npm run build
```

실제 DB 검증은 기존 스키마가 준비된 테스트 DB에 대해 별도로 실행한다. 새 DB라면 개발 서버에 최초 로그인해 기존 스키마 초기화를 완료한다.

```bash
WORKSPACE_DB_CHECK=1 node --env-file=.env.local --import tsx tests/workspace-inbox.integration.ts
```

이 테스트는 별도 tenant 두 개·종료 상담 205건·대기 상담·메시지를 트랜잭션 안에서 생성한다. 대기 누락, 선택 유지, 제한 전 검색, 특수 문자 검색, 공간 격리를 검증하고 **전체 롤백**한다. 기존 고객 데이터나 외부 채널로 메시지를 보내지 않는다.

정상 종료 시 `검증 통과` 메시지와 종료 코드 0을 확인한다. 환경변수를 생략하면 실제 DB 검증은 실행되지 않고 안내만 출력하므로 이를 통과로 기록하지 않는다.

기존 `middleware`를 `proxy`로 옮기라는 Next.js 안내는 알려진 기존 항목이다. 새 빌드 오류와 구분해서 기록한다.
