# Ideal AI 챗봇 운영 기능 확장 PRD

- 작성일: 2026-10-05
- 상태: 첫 출시 범위 구현 및 로컬 검증 완료. 운영 반영에는 배포 필요
- 대상: Ideal AI Chatbot SDK 관리자 서비스, 웹 위젯, 공개 SDK
- 개발 순서: ① 미응답 질문 → Q&A 등록 → ④ 상담 인계 요약 → ⑤ URL 지식 가져오기 → ⑦ 견적·상담 신청 폼
- 범위: 네 기능의 첫 출시. 후속 확장은 별도 일정으로 관리한다.

## 1. 제품 목표와 배경

현재 서비스에는 Q&A 및 문서 기반 AI 답변, 위젯/SDK, 대화 기록, 분석, Slack·Telegram 상담원 연결이 있다. 운영자가 질문을 확인하고 지식을 보완하는 작업, 상담원이 대화 맥락을 파악하는 작업, 홈페이지 내용을 등록하는 작업, 고객 문의를 접수하는 작업을 이어주는 것이 이번 확장의 목표다.

기대하는 결과는 다음과 같다.

1. 미응답 발견부터 답변 등록까지의 작업을 한 화면에서 마친다.
2. 상담원에게 고객 문의와 미해결 문제를 함께 전달한다.
3. 공개 웹페이지를 검토 후 챗봇 지식으로 등록하고 갱신한다.
4. 대화를 견적·상담 신청으로 전환하고 처리 상황을 관리한다.

수치 개선 목표는 출시 전 기준 데이터를 수집한 뒤 정한다. 기존 Q&A 분석의 답변 성공률은 Q&A 매칭 여부를 나타내며, 실제 고객 해결률로 해석하지 않는다. 답변 평가·고객 해결 여부 수집은 이번 범위에 포함하지 않는다.

## 2. 사용자와 주요 요구

| 사용자 | 요구 | 제공 가치 |
|---|---|---|
| 고객사 관리자 | 미응답 질문을 쉽게 보완하고 지식을 최신 상태로 유지 | 분석·등록·갱신 흐름 연결 |
| 상담원 | 고객이 이미 받은 안내와 남은 문제 파악 | 인계 요약 및 원문 확인 |
| 방문 고객 | 반복 설명 없이 상담받고 견적·상담 요청 접수 | 대화 맥락을 보존한 인계·신청 |
| 서비스 운영자 | 고객사별 접근 격리, 실패 추적, 안정적인 운영 | 일관된 권한·처리 상태·오류 기록 |

## 3. 공통 제품 요구사항

- 관리자 작업은 로그인한 고객사 소유의 봇에만 허용한다. 봇·폴더·세션·문서 소유권을 각각 검증한다.
- 공개 위젯/SDK 작업은 기존 봇 토큰 검증을 적용한다. 세션 ID만으로 대화나 신청 정보를 읽을 수 없도록 한다.
- 저장 성공과 외부 채널 전송 성공을 구분한다. 외부 알림 실패가 고객의 접수나 상담 연결을 취소하지 않는다.
- 중복 클릭, 네트워크 재시도, 동시 요청에 대해 서버와 DB에서 중복 처리를 방지한다.
- 관리자 시간 표시는 한국 시간 기준으로 제공하고 서버 저장 시간은 기존 규약을 유지한다.
- 로딩·빈 목록·실패·재시도 상태를 제공한다. 폼은 키보드 접근, 입력 라벨, 오류 위치 안내를 지원한다.
- AI가 작성한 내용은 AI 요약임을 표시하고 원문을 확인할 수 있게 한다.
- API 키, 봇 토큰, 불필요한 개인정보를 오류 로그에 기록하지 않는다.
- 기존 Q&A·문서·상담·위젯 동작과 호환되는 방식으로 추가한다.
- 아래 데이터·API 이름은 구현 설계안이다. 착수 시 기존 구조에 맞춰 확정하되 제품 동작과 완료 기준은 유지한다.

## 4. 기능 ① 미응답 질문 → Q&A 등록

### 4.1 문제와 목표

현재 Q&A 분석에서 미응답 질문을 확인할 수 있지만 답변을 등록하려면 별도 관리 흐름이 필요하다. 미응답 목록에서 질문과 대화를 확인하고 바로 Q&A로 보완할 수 있게 한다.

### 4.2 사용자 흐름

1. Q&A 분석에서 미응답 목록과 처리 상태를 확인한다.
2. 질문을 선택해 원문, 일시, 해당 세션 대화를 확인한다.
3. ‘답변 등록’을 누르면 질문이 채워진 입력창이 열린다.
4. 질문을 필요에 따라 편집하고 답변과 폴더를 지정한다.
5. 등록하면 임베딩 생성 및 Q&A 저장 후 보완 완료로 표시한다.
6. 처리할 필요가 없는 항목은 ‘제외’하고, 필요하면 미처리로 되돌린다.

### 4.3 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| QA-01 | 기간·미처리/보완 완료/제외 필터와 페이지 이동 지원 | 필수 |
| QA-02 | 질문 원문·일시·세션 대화 확인 | 필수 |
| QA-03 | 질문·답변·폴더 입력과 기존 임베딩 처리 재사용 | 필수 |
| QA-04 | 미응답 로그와 생성 Q&A 연결 기록 | 필수 |
| QA-05 | 등록 중 재제출 방지 및 동일 항목 중복 등록 방지 | 필수 |
| QA-06 | 기존 동일 질문이 있으면 안내하고 기존 Q&A 연결 허용 | 필수 |
| QA-07 | 동일 질문의 발생 횟수 표시 및 빈도순 정렬 | 후속 |
| QA-08 | 의미가 비슷한 질문 묶기와 AI 답변 초안 | 후속 |

첫 출시의 처리 단위는 개별 미응답 로그다. 한 항목을 보완했다고 유사 질문 전체를 자동 완료 처리하지 않는다. 기존 동일 질문 비교는 공백·대소문자 등 제한된 정규화를 사용한다.

### 4.4 데이터 및 API 설계안

- 기존 `chat_logs`, `qa_pairs`, `qa_folders`를 활용한다.
- 미응답 처리 기록: 로그 ID, 봇 ID, 상태(`pending/resolved/excluded`), 연결 Q&A ID, 처리 시각. 로그 ID에 유일 제약을 둔다.
- 기록이 없는 기존 미응답은 미처리로 간주한다.
- 연결 Q&A가 삭제되면 ‘연결 답변 삭제됨’을 표시하고 다시 보완할 수 있게 한다.
- `GET /api/bots/{id}/unanswered`: 기간·상태·페이지별 목록.
- `POST /api/bots/{id}/unanswered/{logId}/resolve`: 새 Q&A 생성 또는 기존 Q&A 연결.
- `PATCH /api/bots/{id}/unanswered/{logId}`: 제외·미처리 복원.
- 임베딩은 DB 트랜잭션 전에 생성하고 Q&A 저장과 처리 기록 갱신은 같은 트랜잭션으로 수행한다. 동시 요청은 유일 제약으로 방어한다.

### 4.5 예외와 완료 기준

- 임베딩/API 키/저장 실패 시 입력 내용을 유지하고 항목은 미처리로 남는다.
- 이미 보완된 요청의 재시도는 기존 결과를 반환한다.
- 원문 대화가 없는 과거 로그는 확인 가능한 질문·답변만 표시한다.
- **AC-QA-01:** 분석 화면에서 이동 없이 등록하고 테스트 질문에서 검색된다.
- **AC-QA-02:** 동시에 두 번 요청해도 Q&A가 중복 생성되지 않는다.
- **AC-QA-03:** 등록 실패 시 Q&A와 처리 상태가 불일치하지 않는다.
- **AC-QA-04:** 다른 고객사의 로그·Q&A·폴더 지정은 거절된다.

## 5. 기능 ④ 상담 인계 요약

### 5.1 문제와 목표

상담원이 고객의 이전 대화를 읽는 시간을 줄이고 반복 질문을 줄인다. 요약 생성 실패나 지연은 상담 연결을 막지 않아야 한다.

### 5.2 사용자 흐름과 출력

고객의 기존 상담 연결 요청을 접수하고 최근 대화를 요약한다. 결과는 관리자 상담 화면과 연결된 Slack·Telegram에 전달한다.

출력 항목:

- 문의: 고객이 요청한 내용.
- 이미 안내한 내용: 봇 또는 상담원이 실제로 안내한 내용.
- 남은 문제: 아직 확인·처리되지 않은 사항.
- 고객이 제공한 정보: 상담에 필요한 주문번호 등. 불필요한 개인정보는 제외한다.
- 원문 확인: 관리자 대화 화면 연결. 외부 메시지에는 공개 세션 조회 주소를 넣지 않는다.

### 5.3 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| SUM-01 | 봇별 요약 활성화 설정, 기본값 비활성 | 필수 |
| SUM-02 | 서버에 저장된 최근 대화로 구조화 요약 생성 | 필수 |
| SUM-03 | 요약 상태·결과를 인계 기록에 저장 | 필수 |
| SUM-04 | 관리자 화면 및 Slack·Telegram에 동일 결과 표시 | 필수 |
| SUM-05 | 키 없음·시간 초과·오류 시 최근 대화 발췌 제공 | 필수 |
| SUM-06 | 같은 인계 요청의 중복 생성·전송 방지 | 필수 |
| SUM-07 | 상담 종료 요약 및 Q&A 초안 연결 | 후속 |

입력은 최근 최대 30개 메시지, 총 12,000자로 제한하는 초기안을 적용한다. 제한으로 생략된 경우 ‘최근 대화 기준’으로 표시한다. 출력은 총 1,500자 이내를 목표로 한다. 정보가 없으면 ‘확인되지 않음’으로 표시한다. 대화에 포함된 지시문은 요약 대상 데이터로 취급한다.

### 5.4 처리·데이터 설계안

- 기존 `chat_messages`, `chat_sessions`, `support_handoffs`를 활용한다.
- 인계에 요약 상태(`pending/generated/fallback/disabled`), 구조화 결과, 입력 마지막 메시지 ID, 생성 시각, 오류 분류를 저장한다.
- 요약 서비스는 봇의 공급자 설정·고객사 API 키를 사용하며 모델 호환성을 검증한다.
- 기존 인계 API에 연결한다. 첫 인계 알림은 즉시 전송하고 요약은 준비되는 대로 같은 Slack 스레드·Telegram 토픽에 추가한다.
- 생성 시간 제한 초기값은 5초. 시간 초과 시 발췌를 사용하고 늦게 도착한 요약은 중복 전송하지 않는다.
- 작업 실행·재시도 방식은 배포 환경에 맞는 지속 가능한 작업 처리 방식으로 확정한다. 응답 이후의 임의 비동기 실행에 의존하지 않는다.
- 채널별 전송 상태를 기록하고 성공한 채널은 재전송하지 않는다.
- AI 요약 사용 시 추가 모델 비용이 발생함을 활성화 설정에 설명한다.

### 5.5 완료 기준

- **AC-SUM-01:** 원문에 없는 주문번호·고객 사실·처리 완료 여부를 생성하지 않는다.
- **AC-SUM-02:** 요약 생성 오류·시간 초과 시에도 인계가 접수된다.
- **AC-SUM-03:** 두 채널 중 하나가 실패해도 다른 채널의 전송과 저장은 완료된다.
- **AC-SUM-04:** 재요청해도 동일 인계에 요약 알림이 중복되지 않는다.
- **AC-SUM-05:** 짧은 대화·빈 대화·긴 대화에 각각 적절한 요약 또는 발췌가 나온다.

## 6. 기능 ⑤ 사이트 URL로 지식 가져오기

### 6.1 문제와 목표

공개 홈페이지·FAQ를 문서로 준비하는 작업 없이 지식에 추가한다. 수집 내용을 검토한 뒤 반영하고 재수집 실패가 기존 지식을 훼손하지 않게 한다.

### 6.2 첫 출시 범위와 흐름

1. 문서 관리에서 ‘URL 가져오기’를 선택한다.
2. 공개 HTML 페이지 주소를 입력한다.
3. 수집 상태와 추출한 제목·본문·최종 주소를 확인한다.
4. 제목·본문을 수정하고 폴더를 선택해 저장한다.
5. 문서 목록에서 원본 URL·마지막 확인·마지막 반영 시각을 확인한다.
6. ‘다시 가져오기’를 누르면 변경 여부와 이전/새 내용을 비교한다.
7. 관리자가 반영을 선택해야 기존 문서와 임베딩이 교체된다.

### 6.3 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| URL-01 | 공개 단일 HTTP/HTTPS HTML 페이지 가져오기 | 필수 |
| URL-02 | 메뉴·푸터·스크립트 등 제외하고 본문 추출 | 필수 |
| URL-03 | 저장 전 미리보기·편집·폴더 선택 | 필수 |
| URL-04 | 동일 봇에서 동일 URL 중복 안내 | 필수 |
| URL-05 | 재수집·변경 비교·관리자 승인 반영 | 필수 |
| URL-06 | 실패 사유 및 기존 문서 보존 | 필수 |
| URL-07 | 같은 사이트 하위 페이지·사이트맵 수집 | 후속 |
| URL-08 | 정기 재수집·변경 알림·선택적 자동 반영 | 후속 |

로그인 페이지, PDF 등 비HTML URL, 브라우저 실행이 필요한 페이지, CAPTCHA 우회는 지원하지 않는다. 기존 파일 업로드는 그대로 이용한다. 이용 제한·robots 정책으로 수집할 수 없는 페이지는 우회하지 않고 사유를 안내한다.

### 6.4 수집 제한 및 데이터 설계안

- 초기 제한: 요청 전체 15초, 리디렉션 최대 3회, 응답 본문 최대 2MB, 추출 본문 최대 50,000자. 초과 시 자동 잘라 저장하지 않고 안내한다.
- URL 스킴·주소·DNS 결과를 검증한다. 로컬·사설·예약 IP, 클라우드 메타데이터 주소, 인증정보 포함 URL을 차단한다.
- 최초 요청과 매 리디렉션에서 재검증하고 연결 시에도 검증된 IP 정책을 적용해 DNS 변경 우회를 방지한다.
- 수집된 HTML은 실행하지 않는다. 미리보기는 텍스트로 표시한다.
- URL 정규화는 프래그먼트 제거·호스트 정규화를 적용하고 의미가 달라질 수 있는 쿼리 파라미터는 임의 제거하지 않는다.
- `documents`와 연결한 웹 원본 기록: 입력/최종 URL, 원본 본문 해시, 마지막 확인 시각, 마지막 반영 시각, 수집 상태·오류.
- 검토용 수집 결과는 활성 지식과 분리 저장하며 보관 기한을 적용한다.
- 관리자 편집 내용과 재수집 원문을 구분한다. 원본 변화는 원본 해시로 판단하고 반영 화면에서 편집 내용이 교체됨을 안내한다.
- 본문이 바뀌지 않으면 기존 임베딩을 유지한다. 변경 시 임베딩 생성 성공 후 본문과 임베딩을 함께 교체한다.
- 문서 삭제 시 연결 원본·검토 결과도 정리한다.

### 6.5 API 설계안

- `POST /api/bots/{id}/web-sources/preview`: URL 수집 및 미리보기 결과 생성.
- `POST /api/bots/{id}/web-sources`: 검토 결과를 문서로 등록.
- `POST /api/bots/{id}/web-sources/{sourceId}/refresh`: 재수집 및 변경 비교 생성.
- `POST /api/bots/{id}/web-sources/{sourceId}/apply`: 검토한 내용을 기존 문서에 반영.
- 미리보기 ID는 고객사·봇에 귀속된다. 반영 시 문서 버전을 확인해 동시 수정 덮어쓰기를 막는다.

### 6.6 완료 기준

- **AC-URL-01:** 일반 공개 FAQ를 가져와 검토 후 저장하고 챗봇 검색에 활용한다.
- **AC-URL-02:** 변경 없는 재수집은 문서·임베딩을 다시 생성하지 않는다.
- **AC-URL-03:** 추출·임베딩·저장 실패 시 기존 지식은 유지된다.
- **AC-URL-04:** 차단 주소로 직접 요청하거나 리디렉션해도 내부망에 연결하지 않는다.
- **AC-URL-05:** 빈 본문·비HTML·시간 초과·크기 초과·지원하지 않는 페이지를 구분해 안내한다.

## 7. 기능 ⑦ 견적·상담 신청 폼

### 7.1 문제와 목표

대화 중 발생한 견적·상담 수요를 구조화해 접수하고 관리한다. 실시간 상담 인계와 별개의 신청이며, 운영 시간 밖에도 접수할 수 있다.

### 7.2 사용자 흐름

1. 관리자가 봇별 견적·상담 폼을 활성화하고 항목·안내문을 설정한다.
2. 고객이 위젯의 ‘견적 요청’ 또는 ‘상담 신청’을 누른다.
3. 항목을 입력하고 개인정보 수집 안내에 동의한다.
4. 제출 후 접수번호와 안내를 확인한다.
5. 관리자는 접수 목록에서 내용·동의 기록·연결 대화·요약을 확인한다.
6. 상태를 신규 → 처리 중 → 완료로 변경하고 메모를 남긴다.
7. Slack·Telegram에 알림을 전송하고 실패 시 관리자에게 재시도를 제공한다.

### 7.3 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| LEAD-01 | 봇별 견적·상담 유형 활성화 및 폼 설정 | 필수 |
| LEAD-02 | 이름·회사명·이메일·전화번호·문의 내용 제공 | 필수 |
| LEAD-03 | 항목 사용 여부·필수 여부 설정 | 필수 |
| LEAD-04 | 개인정보 안내·명시적 동의·동의 버전 저장 | 필수 |
| LEAD-05 | 위젯 폼·SDK 제출 API·접수번호 반환 | 필수 |
| LEAD-06 | 접수 목록·검색·유형/상태/기간 필터·상세 화면 | 필수 |
| LEAD-07 | 신규/처리 중/완료 상태와 내부 메모 | 필수 |
| LEAD-08 | 연결 대화·2단계 요약·채널별 알림 및 재시도 | 필수 |
| LEAD-09 | 중복 제출 방지·속도 제한·입력 검증 | 필수 |
| LEAD-10 | CSV·담당자 배정·이메일·CRM·자연어 폼 제안 | 후속 |

이름과 문의 내용은 필수이며 연락처는 이메일 또는 전화번호 중 최소 하나를 요구한다. 관리자는 둘 중 하나를 필수로 지정하거나 ‘둘 중 하나’ 규칙을 선택할 수 있다. 두 연락처 모두 사용하지 않는 설정은 저장할 수 없다. 회사명은 기본 선택 항목이다. 첨부파일과 자유로운 필드 빌더는 첫 출시 범위에서 제외한다.

### 7.4 상태·데이터·API 설계안

- 접수 상태: `new/in_progress/completed`. 관리자가 재처리를 위해 이전 상태로 바꿀 수 있고 변경 이력을 남긴다.
- 신청 기록: ID·접수번호·고객사/봇 ID·신청 유형·검증된 세션 연결·연락처·문의·상태·생성/변경 시각.
- 동의 기록: 동의 시각·안내문 버전 및 당시 문구 스냅샷. 관리자 문구 변경은 과거 기록에 영향을 주지 않는다.
- 메모와 상태 변경 이력, 요약 결과, 채널별 전송 상태를 별도로 관리한다.
- 공개 폼 설정 응답에는 위젯에 필요한 항목·안내문만 포함한다.
- `POST /api/chat/{botId}/requests`: 공개 접수. 봇 토큰·입력·동의·서버 설정·세션 소유 검증.
- `GET /api/bots/{id}/requests`: 관리자 접수 목록.
- `GET /api/bots/{id}/requests/{requestId}`: 관리자 상세.
- `PATCH /api/bots/{id}/requests/{requestId}`: 상태 수정.
- `POST /api/bots/{id}/requests/{requestId}/notes`: 내부 메모.
- `POST /api/bots/{id}/requests/{requestId}/notifications/retry`: 실패 채널 재전송.
- SDK에 폼 설정 조회와 신청 제출 메서드를 추가하고 문서·타입·배포 산출물을 함께 갱신한다.
- 제출마다 클라이언트가 생성한 멱등성 키를 사용하며 봇 ID와 함께 유일 제약을 둔다. 같은 키의 같은 요청은 기존 접수 결과를 반환하고 다른 본문이면 충돌을 반환한다.
- 신청과 알림 작업을 함께 저장한 후 접수 성공을 반환한다. 요약·외부 알림은 실패해도 접수 결과에 영향을 주지 않는다.
- 신청은 채팅 월 세션 한도와 별도 집계한다. 비활성 구독·비활성 폼은 접수를 허용하지 않는다. 접수 자체가 새 채팅 세션을 소비하지 않는다.

### 7.5 개인정보와 완료 기준

- 외부 채널에는 신청 유형·접수번호·문의 요약·관리자 상세 링크를 기본 전송한다. 전체 연락처는 기본적으로 관리자 상세에서 확인한다.
- 공개 접수 응답은 다른 신청의 개인정보나 진행 상태를 조회하는 수단으로 사용하지 않는다.
- 개인정보 안내에는 목적·항목·보유 기간·거부 안내를 설정한다. 실제 보관 정책과 일치하지 않는 문구로 폼을 활성화하지 않는다.
- 보유 기간 만료 시 개인정보·동의 스냅샷·연결 요약·메모에 포함된 개인정보를 정리한다. 자동 삭제 작업과 운영 확인 방법을 출시 전에 확정하고 검증한다.
- **AC-LEAD-01:** 견적·상담 신청이 저장되고 고유 접수번호를 반환한다.
- **AC-LEAD-02:** 알림 실패·요약 실패에도 접수 성공이 유지된다.
- **AC-LEAD-03:** 중복 클릭·동시 요청·재시도에서 신청이 한 건만 생성된다.
- **AC-LEAD-04:** 다른 고객사의 신청·세션에 접근하거나 연결할 수 없다.
- **AC-LEAD-05:** 필수값·연락처·동의 검증을 서버에서도 수행한다.
- **AC-LEAD-06:** 관리자가 목록과 대화를 확인하고 상태·메모를 관리한다.
- **AC-LEAD-07:** 보유 기간 만료 데이터가 정리되고 개인정보가 알림·로그에 불필요하게 남지 않는다.

## 10. 검증과 출시 조건

### 기능별 검증

- Q&A: 정상 등록, 기존 연결, 임베딩 실패, 동시 요청, 연결 답변 삭제, 타 고객사 접근.
- 요약: 정상/빈/긴 대화, 원문에 없는 정보, 입력 내 지시문, 공급자 오류, 시간 초과, 한 채널 실패, 중복 인계.
- URL: 정상 HTML, 빈 본문, 비HTML, 리디렉션, 내부 주소 차단, DNS 변경, 크기 초과, 미변경·변경 재수집, 동시 수정.
- 폼: 각 신청 유형, 연락처 규칙, 동의 누락, 설정 변경, 중복 제출, 잘못된 세션, 비활성 구독, 외부 전송 실패, 보관 만료 정리.

### 통합 시나리오

1. 미응답 질문 발생 → 분석 화면에서 Q&A 보완 → 같은 질문 검색 확인.
2. 공개 FAQ 수집 → 검토·등록 → 해당 내용을 활용한 대화 → 변경 수집·반영.
3. 고객 대화 → 상담 연결 → 관리자·Slack·Telegram에서 요약과 원문 확인.
4. 대화 중 견적 신청 → 접수번호 확인 → 관리자 내용 확인·처리 완료.
5. AI 공급자 또는 외부 채널 실패 상황에서 상담·접수 데이터 보존 확인.

출시 조건은 해당 단계의 모든 필수 요구사항과 완료 기준 충족, 기존 위젯·SDK·상담 흐름의 회귀 확인, DB 변경의 기존 데이터 호환성 확인, 오류 확인·재시도 방법 문서화다. 문제가 발생하면 기능을 비활성화해 추가 처리를 중단하되 기존 데이터는 유지한다.

## 13. 구현 결과

구현 위치, 확인 순서, 테스트 결과, 운영 설정은 [확인 가이드](OPERATIONS-REVIEW.md)에 정리했다. API는 상세 설계에서 일부 액션을 기존 리소스 경로의 POST/PATCH로 통합했다. 상담 인계는 기존 봇별 단일 채널 정책을 유지하고 신청 알림은 연결된 채널별로 처리한다. 후속 확장 범위는 이번 구현에 포함하지 않는다.
